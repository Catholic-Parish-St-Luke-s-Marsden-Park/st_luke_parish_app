## Test Strategy
This slice is still frontend-only static content — hero copy, a typed leadership config, shared AppBar chrome, and a hardcoded-response quick-reply screen. No network/scraping layer exists yet, so the "loading / network failure / missing selector / invalid URL" states from `CLAUDE.md`'s coverage expectations don't apply to new data-fetching code (there is none). Instead, "loading/success/empty/error" is interpreted as the analogous states that do exist in this feature:
- Ask Luke's initial state (no topic selected / welcome bubble only) vs. after a chip tap (response now showing) — the closest thing to "empty" vs. "success" state in this slice.
- The "no link" (non-tappable) row for Ged Oblea vs. the "linked" rows — an error-adjacent/edge-case UI branch (`onTap: null` vs. wired), tested explicitly.
- URL validation itself (`UrlLauncherService.launchExternal`'s scheme/host checks) is existing, unmodified library code from the coder phase; not re-derived from a BA REQ, so not retested here beyond confirming the injected fake receives the exact URL — a "does it launch what leadership config says" concern, not a "does url_launcher's internal validation logic work" concern.

Widget tests are used throughout (per `CLAUDE.md`'s required test types) with `UrlLauncherService` injected via Riverpod's `overrideWithValue` so leadership-entry tap behavior is verified without touching platform channels. Unit tests are used for pure config/data assertions (list contents/order, typed model field values) where a widget isn't needed to prove the requirement.

## Test-Authoring Fixes (not implementation bugs — test-file corrections made while authoring)
1. **`ensureVisible` + extra `pumpAndSettle` needed before tapping leadership rows.** The `ParishScreen`'s `ListView` is taller than the default `800x600` test viewport, so the Bishop/Fr Gayan/Ged Oblea rows initially fell outside the hit-testable render view and `tester.tap()` warned/failed to register the tap. Fixed by calling `tester.ensureVisible(...)` (scroll into view) followed by an explicit `pumpAndSettle()` before each tap. This is a test-authoring detail, not an implementation issue — the app itself scrolls normally.
2. **`find.text('Church Leadership')` initially failed.** `SectionLabel` uppercases its label (`label.toUpperCase()`) before rendering, so the actual rendered text is `"CHURCH LEADERSHIP"`, not `"Church Leadership"`. Corrected the assertion to match the actual rendered (uppercased) text. This is expected, intentional widget behavior (an uppercase section-label style), not a bug — confirmed by reading `lib/features/parish/presentation/widgets/section_label.dart`.

No production/`lib/` code was modified to make any test pass. Both fixes above were confined entirely to the new test files.

## Unresolved Coverage Gaps
1. **REQ-F02-015 ("no part of this chrome lives under `lib/features/parish/`")** is verified as a source-location/import-path check (confirmed by successful compilation against `lib/app/shell/widgets/` and `lib/shared/widgets/` import paths, and independently by direct `Read` of every new file's path during this phase), not as a runtime widget-tree assertion — there is no way to assert "which folder a class was compiled from" from within a running widget test. Treated as a structural/code-review-style check rather than a gap in coverage strength, but flagged for transparency since it's a different verification method than the other REQs.
2. **No live device/emulator run.** All verification is via `flutter test`'s headless widget-test harness (as `01-bootstrap-app`'s tester phase also relied primarily on, supplemented there by one iOS simulator screenshot). No Android/iOS simulator was booted in this session, so real AppBar width pressure (logo + 2 pills + hamburger on narrow phones, flagged as a risk in both the BA and coder plans) is not independently confirmed here beyond the fact that `AppPillButton` renders without a Flutter overflow *exception* in the default test viewport. Widget tests do not catch pixel-level clipping that doesn't throw (same category of gap noted in the `01-bootstrap-app` tester plan for a different area). Recommend a live-device spot-check before merge, consistent with the BA's flagged risk.
3. **Image asset quality/licensing** (Vatican News coat-of-arms, Diocese of Parramatta LinkedIn logo) — not a testable concern via `flutter test`; carried forward from the coder plan's Risks/Follow-ups as still open and non-blocking for this phase.
4. **`UrlLauncherServiceImpl`'s real platform-channel behavior** (actual `url_launcher` `canLaunchUrl`/`launchUrl` calls, Android manifest `<queries>` / iOS `LSApplicationQueriesSchemes` wiring for external `https` launches) is not exercised by any test in this repo — by design, since widget tests inject a fake `UrlLauncherService` specifically to avoid touching platform channels. This is existing, unmodified library-wiring code from the coder phase (not itself a BA REQ), so no new gap was introduced here, but it means "does tapping a leadership row actually open a real browser on a real device" remains unverified by any automated test, past or present. A manual on-device tap-through is the appropriate follow-up (Verifier/Deployer phase territory, not blocking Tester sign-off).
5. **Golden/visual regression tests** — none added for the new Hero/About/Leadership/AskLuke UI, consistent with `01-bootstrap-app`'s tester-phase judgment call that golden tests are premature while the UI is still expected to evolve; flagged for a future feature slice if/when this UI stabilizes, per `CLAUDE.md`'s golden-test guidance for "stable, important UI states."
