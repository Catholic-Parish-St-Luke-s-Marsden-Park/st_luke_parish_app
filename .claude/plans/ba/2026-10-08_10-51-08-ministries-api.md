## Feature Summary
The Ministries tab and its detail screen read ministries from the parish API instead of a hardcoded list, so staff can change ministries without an app release. The last good response is cached on the device, and a snapshot bundled with the app covers the first launch with no network. What the user sees stays the same.

## In Scope
- A data layer for ministries: remote datasource, JSON parser, `shared_preferences` cache, bundled fallback and repository.
- Stale-while-revalidate on the list, pull-to-refresh, and loading, error and empty states.
- Detail lookup by id from the loaded list, falling back to `GET /v1/ministries/{id}`.
- Entity changes: drop `emoji`, and replace `ctaEmail` with `contactEmail` + `emailSubject`.
- `API_BASE_URL` configuration with a fallback to the origin of `BASE_URL`.
- A hook for injecting request headers later, for App Check.
- `CLAUDE.md`, README and ADR updates.

## Out of Scope
- Ministry photos (not in the API yet).
- Push notifications when content changes.
- ETag / `If-None-Match`.
- `firebase_app_check`.
- Changing the existing card or detail layout.
- Pre-existing accessibility gaps in the Ministries layout, such as `_StatChip`'s 9pt label and the missing text-scale sweep for the grid. These are logged as a risk.

## Assumptions
- The API was seeded with exactly the 16 ministries and 4 categories in `static_ministries_config.dart`. A one-off parity check in the coder phase confirms this before the config is deleted.
- Every field is always present, `emailSubject` may be `""`, and unknown fields may be added later.

## Risks
- Fallback asset drift: the bundled snapshot goes stale unless it is refreshed at release time.
- `API_BASE_URL` points at production even in debug builds. The endpoints are public and read-only.
- Pre-existing accessibility gaps in the Ministries layout (see Out of Scope).

## Unknowns / Open Questions
- None blocking.

## Acceptance Criteria

### Data source and parsing
- `REQ-F08-001`: The app fetches `GET {apiBase}/v1/ministries` with a 10s timeout, decoding the body as UTF-8 from the raw bytes.
- `REQ-F08-002`: A non-200 response, a timeout or a transport error becomes a typed `MinistriesNetworkFailure`.
- `REQ-F08-003`: A missing or ill-typed required field becomes a typed `MinistriesParsingFailure` naming the field.
  - Malformed JSON gets the same failure.
  - Unknown fields are ignored.
- `REQ-F08-004`: Categories and ministries render in the order the API returns them. Nothing is sorted on the device.
- `REQ-F08-005`: The datasource accepts injected request headers, for a future `X-Firebase-AppCheck` header. None are sent today.

### Configuration
- `REQ-F08-006`: `API_BASE_URL` in `assets/app.env` gives the API origin and is validated like `resolveBackendUri`:
  - it must be an absolute http(s) URL, and https in release builds;
  - a path is reduced to the origin;
  - a set but invalid value gives no API base, with the reason logged.
- `REQ-F08-007`: When `API_BASE_URL` is unset or blank, the origin of a valid `BASE_URL` is used.
- `REQ-F08-008`: With no valid API base, no request is made. The failure is treated like a network failure, so the cache or fallback is shown.

### Offline behaviour
- `REQ-F08-009`: With a cached response, the list shows the cache immediately, refreshes in the background, and replaces and saves the cache on success.
- `REQ-F08-010`: If the background refresh fails, the cached copy stays on screen and in storage.
- `REQ-F08-011`: With no cache and no network, the list shows `assets/ministries_fallback.json`, a snapshot of `GET /v1/ministries`.
  - The bundled copy is never written to the cache.
  - The snapshot replaces `static_ministries_config.dart`.
- `REQ-F08-012`: A corrupted cache entry is treated as a miss, not a crash.

### List screen
- `REQ-F08-013`: The Ministries tab shows explicit states:
  - loading;
  - error, with a message and a "Try again" button at least 48px tall;
  - empty;
  - data, with the existing hero, category headers and cards.
- `REQ-F08-014`: Pull-to-refresh fetches from the network. On success the list is replaced. On failure the current list stays and a SnackBar says so.

### Detail screen
- `REQ-F08-015`: The detail screen looks the ministry up by id in the loaded list. If the id isn't there, it fetches `GET /v1/ministries/{id}`.
- `REQ-F08-016`: A 404 from the detail fetch shows the existing "Ministry not found." screen. Any other failure shows an error message with a retry.

### Entity and CTA
- `REQ-F08-017`: The `Ministry` entity has no `emoji` field, and `ctaEmail` is replaced by `contactEmail` and `emailSubject`.
- `REQ-F08-018`: The Join CTA launches `Uri(scheme: 'mailto', path: contactEmail, query: 'subject=' + Uri.encodeComponent(emailSubject))` through `UrlLauncherService.launchExternal`, so spaces are `%20`, not `+`.
  - When the subject is empty, there is no query.
  - Example: `mailto:marsdenpark@parracatholic.org?subject=Music%20Ministry%20Interest`.

### Content parity and rules
- `REQ-F08-019`: The fallback asset holds the same 16 ministries in 4 categories, in the same order, as the old static config. The sacramental programme still uses `sacraments@stlukesmarsdenpark.org.au`.
- `REQ-F08-020`: `CLAUDE.md` allows the parish API's public, read-only endpoints and forbids its `/admin` console. The README documents `API_BASE_URL` and how to refresh the fallback asset.

### Quality gates
- `REQ-F08-021`: The issue's test list is covered: DTO parsing including a missing and an unknown field; cache then network; network failure keeps the cache; no cache and offline uses the fallback; `API_BASE_URL` resolution; the detail 404 path. The widget tests are driven by a fake repository loaded from the fallback JSON.
- `REQ-F08-022`: `dart format`, `flutter analyze` and `flutter test` are clean. Generated `.g.dart` files are committed with their sources. Shell tests don't touch the network for Ministries.
