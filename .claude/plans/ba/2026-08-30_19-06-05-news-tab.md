## Feature Summary
Replace the News tab's generic `PlaceholderScreen` stub with a real screen showing: (1) a "Latest Bulletins" section backed by live data — up to 6 bulletin PDFs fetched from the parish's WordPress bulletins-category RSS feed, parsed via XML + regex (not CSS selectors), explicitly re-sorted newest-first, with the newest item labeled "LATEST" and the rest "PREVIOUS", and empty/error states that include a fallback link to the parish's bulletins page; (2) a "Parish News" section with exactly 2 static announcement entries; and (3) a "Submit a Prayer Request" section with a static Prayer Intentions card and an external-link CTA (confirmed URL) reusing the existing `UrlLauncherService`. This is the first feature in the app with real async network content, so it must fully implement CLAUDE.md's `AsyncValue`-based loading/success/empty/error handling — unlike every prior feature, which used static config only. No icons/emoji anywhere in the UI. This is a thin vertical slice for the News tab only; no other tab, and no CSS-selector scraping infrastructure, is touched.

- `lib/features/news/data/parsers/` — XML parsing (via the `xml` package) + regex extraction logic, returning typed raw/DTO models, not raw XML/DOM, to the repository. Implements:
  - Iterate `<item>` elements, capped at 6.
  - PDF link: regex `href="([^"]+\.pdf[^"]*)"` (case-insensitive) against `content:encoded`, falling back to `description` if `content:encoded` is empty/absent.
  - PDF link fallback: if no regex match, use the item's `<link>` URL.
  - Date: parse `<pubDate>` (RFC 822) into a typed `DateTime`.
  - URL validation before any extracted link is exposed to the domain/UI layer.
- `lib/features/news/data/repositories/` — repository implementation orchestrating fetch -> parse -> validate -> sort -> map to `Bulletin`, converting network/parsing failures into explicit typed failures (not raw exceptions). This is the sole access point for bulletin data; screens/widgets/providers must not call the datasource or parser directly.
- Explicit descending sort by parsed `pubDate` applied in the repository (or a clearly-named sorting step) as a safety net independent of feed order, before the first/rest "LATEST"/"PREVIOUS" split is computed.
- `lib/features/news/data/config/` (or equivalent) — static config for the 2 announcement entries, the static Prayer Intentions content (quote, body text, CTA URL), and the bulletins-page fallback URL used by the empty/error states.
- `lib/features/news/presentation/providers/` — a Riverpod `AsyncNotifier`/`FutureProvider` (generated via `riverpod_generator`, `.g.dart` committed alongside its source) exposing bulletins as `AsyncValue<List<Bulletin>>`, `autoDispose` (no caching across screen entries).

- `lib/features/news/presentation/widgets/` — small reusable widgets: bulletin list tile (LATEST/PREVIOUS text pill + title + date + "Download PDF ↗" text-glyph tap target), announcement list item (badge text + title + body + date), prayer intentions card (quote + body + CTA button), section headers, loading/error/empty state views for the bulletins section (error/empty states include a "View bulletins on the parish website" fallback link).

## Risks
- **RSS-vs-CSS-selector deviation requires an ADR (Coder phase, not optional).** CLAUDE.md's Scraping Strategy section states CSS selectors are the default and XPath is "an exception when CSS selectors cannot reliably express the target" — it does not explicitly anticipate a feed+regex mechanism. This feature deviates by using RSS XML + regex extraction instead, reusing proven logic from a working reference app rather than an unverified from-scratch CSS scrape of the rendered `/#bulletins` page (whose structure has never been confirmed to reliably expose the PDF links via selectors, and which the reference app's own author apparently also avoided). The "public content only" rule is still honored — RSS is public parish content, same as the rendered page would be — the deviation is in *mechanism*, not in what is scraped or the public-content constraint. **This must be documented via an ADR during the Coder phase**, following the precedent of ADR-0001/0002/0003 in this repository, before or alongside implementation — not deferred or skipped.
- **Live RSS feed structure has not been verified against the real site during this BA phase.** The feed URL, `<item>`/`content:encoded`/`description`/`pubDate` element names, and the `href="...pdf..."` pattern are all carried over from a working reference app's implementation, not independently re-confirmed live by this BA session. It is plausible but unconfirmed that the live feed's actual XML shape, PDF-link markup, or `pubDate` format differs in some way (e.g. WordPress plugin differences, feed caching/CDN behavior, or PDF links embedded differently). Coder/Tester must perform a live fetch against the real feed early, per CLAUDE.md's "live integration tests against the real site are allowed and expected for scraping verification" rule, rather than relying solely on the reference app's fixture-based confidence.
- **First real network/async feature in this app.** Unlike every prior feature (static config only), this is the first place `AsyncValue`, typed network/parsing failures, timeouts, and retry/empty UX patterns are exercised end-to-end — there is no existing precedent in this codebase to follow exactly, only CLAUDE.md's general rules and the reference app's (partial, less rigorous) example. Slightly higher implementation risk than prior feature slices as a result; mitigated by the explicit, itemized acceptance criteria below covering every CLAUDE.md-required test state.
- **New dependencies (`http`, `xml`).** Both are mature, widely-used Dart packages consistent with CLAUDE.md's "prefer mature, stable packages" rule, and both are already proven working in the reference app — low risk, but this is the first feature to add network-capable dependencies to this project's `pubspec.yaml`, worth flagging for Deployer's manifest/permission checklist (the existing RISK-005 precedent — missing release-build Android `INTERNET` permission — is directly relevant here, since this feature is this app's second network-capable feature and would surface the same class of release-build failure if RISK-005 is not fixed before this feature ships).
- **Static content drift**, same class of risk as 04-masses-tab: the 2 static announcements and the Prayer Intentions static text will silently go stale if the parish's actual news changes, with no staleness detection in this feature (acceptable for Phase 1 per CLAUDE.md, but worth surfacing explicitly).
- **Feed item count below 6 / zero items.** If the parish currently has fewer than 6 (or zero) bulletin posts in the category feed, the UI must handle that gracefully (empty-result state, now with a confirmed fallback link) rather than assuming 6 items always exist — explicitly covered in Acceptance Criteria, not a blocking risk, but worth naming since the reference app's own UI logic was not deeply tested against a genuinely empty feed either.
- **A second external-link surface (bulletins fallback link) is added by the confirmed empty/error-state decision.** This is a `https:` launch through the same existing `UrlLauncherService` pattern as the Prayer Intentions CTA and prior features' external links — it inherits, but does not worsen, the pre-existing RISK-003 (Android manifest `<queries>` gap)/RISK-004 (iOS unverified) risk category; no new risk class is introduced.

## Acceptance Criteria

### Bulletins — data fetch & parsing
- `REQ-F05-001` — The app fetches `https://stlukesmarsdenpark.org.au/category/bulletins/feed/` via the `http` package from a datasource under `lib/features/news/data/datasources/`, with a bounded request timeout; no screen, widget, or provider calls `http` directly.
- `REQ-F05-002` — The XML response is parsed via the `xml` package under `lib/features/news/data/parsers/`, iterating `<item>` elements and capping the result at the first 6 items.
- `REQ-F05-003` — For each item, the PDF link is extracted via case-insensitive regex `href="([^"]+\.pdf[^"]*)"` matched against `content:encoded`; if `content:encoded` is empty or absent, the same regex is matched against `description` instead.
- `REQ-F05-004` — If no PDF regex match is found in either `content:encoded` or `description`, the item's `<link>` URL is used as the bulletin's link instead of a PDF URL.
- `REQ-F05-005` — Each item's date is parsed from `<pubDate>` (RFC 822 format) into a typed `DateTime`; items with an unparseable `pubDate` do not crash the parse and are handled explicitly (e.g. treated as undated, sorted last, or per Coder's documented choice — must not throw an unhandled exception).
- `REQ-F05-006` — The parsed bulletin list is explicitly sorted descending by parsed `pubDate` before display order is determined — this sort is independent of and not assumed to match the feed's own item order.
- `REQ-F05-007` — After sorting, the first bulletin is labeled "LATEST" and every subsequent bulletin is labeled "PREVIOUS", both rendered as plain-text pill labels (no icon/emoji).
- `REQ-F05-008` — Every extracted PDF/link URL is validated (parseable, has a scheme and host) before being exposed to the presentation layer; an item with an unvalidatable URL is handled explicitly (excluded, or flagged non-tappable) rather than passed through silently.
- `REQ-F05-009` — `http` and `xml` are added to `pubspec.yaml` as direct dependencies at their latest stable versions; no CSS-selector-scraping package (e.g. `html`) is added for this feature.

### Bulletins — architecture & failure handling
- `REQ-F05-010` — A `Bulletin` domain entity is defined as a typed, immutable class under `lib/features/news/domain/entities/`, not a dynamic `Map`.
- `REQ-F05-011` — An abstract `BulletinsRepository` contract is defined under `lib/features/news/domain/repositories/`; a concrete implementation under `lib/features/news/data/repositories/` is the sole point that orchestrates fetch, parse, validate, sort, and map to `Bulletin` — no other layer bypasses it to reach the datasource or parser directly.
- `REQ-F05-012` — Network failures (e.g. non-2xx response, timeout, no connectivity) are converted into an explicit typed failure by the repository, not a raw/unhandled exception surfaced to the UI.
- `REQ-F05-013` — Parsing failures (e.g. malformed XML, unexpected feed shape) are converted into an explicit typed failure by the repository, not a raw/unhandled exception surfaced to the UI.
- `REQ-F05-014` — Bulletin data is exposed to the screen via a Riverpod provider under `lib/features/news/presentation/providers/` (generated via `riverpod_generator`, `.g.dart` committed alongside its source in the same commit per CLAUDE.md's generated-code rule) as `AsyncValue<List<Bulletin>>`; the provider is `autoDispose` (no cross-screen-entry caching).
- `REQ-F05-015` — The screen reads bulletins only through this provider (`ref.watch(...)`), never by importing the repository/datasource/parser directly.

### Bulletins — UI states
- `REQ-F05-016` — Loading state: while the provider is loading, the bulletins section shows an explicit, user-friendly loading indicator (not a blank/frozen section).
- `REQ-F05-017` — Success state: on successful fetch with 1+ items, the bulletins section renders each bulletin's title, date, and a "Download PDF ↗" tappable text-glyph affordance, in the sorted (newest-first) order, with the LATEST/PREVIOUS pill per `REQ-F05-007`.
- `REQ-F05-018` — Empty-result state (confirmed): if the fetch succeeds but yields 0 usable bulletin items, the section shows an explicit, user-friendly "no bulletins available" message distinct from the error state, plus a tappable "View bulletins on the parish website" (or equivalent copy) fallback link/button that opens `https://stlukesmarsdenpark.org.au/category/bulletins/` externally via the `UrlLauncherService` pattern.
- `REQ-F05-019` — Parsing-failure state (confirmed): if the feed cannot be parsed, the section shows an explicit, user-friendly error message with no raw exception text/stack trace exposed to the user, plus the same fallback link to `https://stlukesmarsdenpark.org.au/category/bulletins/` as `REQ-F05-018`.
- `REQ-F05-020` — Network-failure state (confirmed): if the fetch fails (timeout, no connectivity, non-2xx), the section shows an explicit, user-friendly error message with no raw exception text/stack trace exposed to the user, distinguishable in content/wording from the parsing-failure message where practical, plus the same fallback link to `https://stlukesmarsdenpark.org.au/category/bulletins/` as `REQ-F05-018`.
- `REQ-F05-021` — Missing/invalid PDF link handling: an item whose PDF link could not be resolved (falls through to `<link>` per `REQ-F05-004`, or fails URL validation per `REQ-F05-008`) is still handled explicitly and predictably in the UI (e.g. still tappable via the page-link fallback, or clearly marked/excluded) — never a silent crash or a dead/broken tap target with no visible indication.
- `REQ-F05-022` — Tapping "Download PDF ↗" (or the page-link fallback), and tapping the empty/error-state fallback link (`REQ-F05-018`/`REQ-F05-019`/`REQ-F05-020`), launches the URL externally via the same launch mechanism established for external links in this app (`url_launcher`/`UrlLauncherService`); none of these tap targets silently no-op.
