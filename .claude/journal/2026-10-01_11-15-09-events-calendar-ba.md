# BA Phase Journal — 08-events-calendar

- 2026-10-01: Drafted `.claude/plans/ba/2026-10-01_11-15-09-events-calendar.md` for a new live "Upcoming Events" section on the News tab (above Bulletins), sourced from the parish website's AI1EC WordPress calendar feed, plus a per-event "Add to my calendar" export action. Scope locked in via three rounds of user clarification across this session:
  1. Both an in-app live calendar view and per-event export (not just one).
  2. Everything in the live feed (not filtered to Masses only).
  3. Placement: News tab, above Bulletins (a custom placement, not one of the originally offered options).
  4. Export: add individual events one at a time (not a bulk subscribe link).
  5. A user-supplied reference screenshot (a "What's On" card from the parish's own other app) set the row visual language: date pill, bold title, italic location, "Details" link — adopted, minus its header icon (this app's established no-icon rule).
  6. Pagination: inline section shows only the next 7 days; a "View all upcoming events" link opens a separate paginated screen for the rest.
  7. Per-event actions: both "Details" and "Add to my calendar" shown side-by-side on each row — then refined again when the user asked whether "Details" could be an in-app popup instead of leaving the app; changed to an in-app bottom sheet built from fields already parsed from the feed, with any feed-provided URL demoted to an optional secondary link inside that sheet.
- Research performed directly this session: identified the live site's AI1EC plugin and its export URL/robots.txt scope; then found and read the user's own other parish app repo on their machine (`stlukes-marsden-park-app`, a Netlify PWA) — `netlify/functions/events.mjs` and `index.html`'s `loadEvents()` are a live, production implementation of this exact fetch. This resolved what would otherwise have been three separate unverified assumptions: the exact feed URL (confirmed working in production), that recurring events are `RRULE`-bearing `VEVENT` templates rather than pre-expanded instances (confirmed — though this feature needs genuine window-bounded expansion, more than the reference's "next occurrence only" shortcut), and that every event always has somewhere for "Details" to point (confirmed, with a generic fallback). Also confirmed the `DTSTART;TZID=Australia/Sydney` floating-local-time format and a portable "fake UTC" technique for handling it without a full timezone database.
- Verified real pub.dev packages exist and fit: `rrule` (^0.2.18 at time of writing — `RecurrenceRule.fromString()` + `.getInstances(start:, after:, before:)`) for RRULE expansion, and `add_2_calendar` (^3.1.1) for the per-event export action (opens the native Calendar app, no Android calendar permission needed for the default flow; iOS needs `NSCalendarsUsageDescription`/`NSContactsUsageDescription` added to `Info.plist` — flagged for Coder/Deployer).
- User approved the plan as drafted, including both recommendations on the two items that remained genuinely open after the reference-app research: proceeding on the robots.txt reading (reinforced by the parish's own other app already fetching this exact URL in production), and using `add_2_calendar` over `device_calendar`.
- Outputs: BA plan (`REQ-F08-001`..`REQ-F08-039`), this journal, memory/feature-index updates. No `lib/`/`test/` changes in this phase.
- Phase-closed; proceeding directly to CODER_AGENT per user approval.
