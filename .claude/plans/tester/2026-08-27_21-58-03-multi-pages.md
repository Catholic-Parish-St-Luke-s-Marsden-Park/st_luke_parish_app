## Test Strategy
- Reused the `_FakeUrlLauncherService implements UrlLauncherService` pattern established in 02-parish-tab's `parish_screen_test.dart` for every external-link test (Ministries CTA, Contact tiles/map), overriding `urlLauncherServiceProvider` via `ProviderScope.overrides` — no platform channels touched.
- Added a `launchResult: false` mode to the fake to cover the BA plan's required launch-failure/unavailable-handler case (REQ-F03-029) for both Ministries and Contact.
- Built a fake `webview_flutter` platform (`test/helpers/fake_webview_platform.dart`, modeled on `webview_flutter`'s own `example/test/main_test.dart` fake-platform pattern) and registered it globally for every test file via `test/flutter_test_config.dart`, so any widget test that builds `AppShell`, `DonateScreen`, or `SimpleWebViewScreen` — directly or by cycling bottom-nav tabs — no longer crashes with "A platform implementation for 'webview_flutter' has not been set". The fake exposes the last-created `FakeNavigationDelegate` so tests can directly invoke `onPageStarted`/`onPageFinished`/`onWebResourceError` to deterministically simulate the WebView's loading/success/failure states, since a fake in-memory WebView never actually loads network content.
- Added `webview_flutter_platform_interface` as an explicit `dev_dependency` (previously only a transitive dependency) since test code now imports it directly.
- Covered every REQ-F03-029-required test state: Ministries grid render (success) with an explicit no-emoji assertion across every rendered `Text` widget (not just a spot check), Ministries detail render (success) with the same no-emoji assertion, Contact tile list render (success) including the 3 no-action tiles, external-link launches for every action type (`tel`/`mailto`/`https`) each with both a success and a simulated failure case, and all three Donate WebView states (loading/success/failure).
- "Empty result" intentionally not covered for Ministries/Contact, consistent with the BA plan's own note that this state is not applicable to fixed static config.

This is a test-harness sizing issue, not a real UI overflow bug — confirmed separately via `flutter analyze` (no overflow warnings) and the app's own `ListView`'s natural scrollability.
