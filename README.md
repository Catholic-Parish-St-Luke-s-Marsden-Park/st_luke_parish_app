# St Luke's Parish App

A native Android and iOS app for **St Luke's Catholic Parish, Marsden Park** —
Mass times, bulletins, parish news, ministries and contact details on a phone.

The app reads selected **public** content from the parish website
(<https://stlukesmarsdenpark.org.au>). Phase 1 is frontend-only: there is no
backend, and no private or authenticated parish data is used.

- **Platforms:** Android and iOS only. No web or desktop target.
- **Dart SDK:** `^3.11.0` (any recent Flutter stable).
- **State management:** Riverpod, with providers generated by `riverpod_generator`.

## Current state

This repository is at the **bootstrap slice**. What exists today:

- The app shell — themed `MaterialApp.router`, a 6-destination bottom
  navigation bar, and a side drawer with two more destinations.
- The design system — navy/gold/cream palette, Playfair Display + Source Sans 3
  via `google_fonts`, and 12px card / 20px pill corner radii
  (`lib/core/theme/`).
- Mobile-only responsive helpers for phone vs. tablet widths
  (`lib/core/layout/responsive.dart`).
- Eight placeholder screens, one per navigation destination.

Every feature screen is currently a `PlaceholderScreen` stub. **No feature has
its `domain/` or `data/` layer yet** — no scrapers, parsers, models or
repositories exist. Those arrive one feature at a time, following the process
below.

## Quick start

```bash
flutter pub get
dart run build_runner build --delete-conflicting-outputs   # required: providers are generated
flutter run
```

`build_runner` is not optional — `lib/app/shell/nav_index_provider.dart` relies
on generated output (`.g.dart`), and the app will not compile without it. Use
`dart run build_runner watch --delete-conflicting-outputs` while developing.

### Saint of the Day (OpenRouter API key)

The "Saint of the Day" feature calls OpenRouter directly and needs an API key
supplied at build/run time — it is never hardcoded in source (see
`.claude/decisions/0005-saint-of-the-day-direct-openrouter-call.md`):

```bash
flutter run --dart-define=OPENROUTER_API_KEY=sk-or-...
```

For a release build, pass the same `--dart-define` flag to `flutter build`.
Without it, the screen shows a "not configured" message instead of sending an
unauthenticated request. CI/release-build wiring for this define is a
Deployer-phase follow-up for feature 06, not yet automated.

Checks to run before opening a pull request:

```bash
flutter analyze                    # must report "No issues found!"
dart format .
flutter test
```

## Layout

```
lib/
├── main.dart          entry point: ProviderScope + StLukeApp
├── app/
│   ├── app.dart        MaterialApp.router + theme wiring
│   ├── router.dart     go_router: a single '/' route hosting AppShell
│   └── shell/          bottom nav, side drawer, selected-tab provider
├── core/
│   ├── theme/          palette, typography, shapes, ThemeData
│   └── layout/         phone/tablet breakpoints and page padding
├── features/<feature>/ one folder per feature (see below)
└── shared/widgets/     widgets shared across features
```

Navigation is deliberately shallow: `go_router` owns one route (`/` →
`AppShell`), and the two drawer destinations are pushed with the standard
`Navigator` since neither needs a deep-linkable URL.

Each feature follows a layered split — `presentation/` for UI and its
providers, `domain/` for entities and contracts, `data/` for repositories,
scraper clients and parsers. Only `presentation/` exists so far. The rules that
govern those layers (no network calls in widgets, repositories as the sole
access point for external content, parsers returning typed models) are in
**`CLAUDE.md`** — read it before adding a feature.

## Testing

`test/` mirrors `lib/`. The suite currently covers the themed shell,
bottom-navigation behaviour including lazy tab building and `IndexedStack`
state preservation, drawer navigation, the generated nav-index provider, and
absence of layout overflow at small-phone, phone and tablet sizes.

Tests trace to requirement IDs (`REQ-F01-002` and similar) recorded with the
feature that introduced them, so a test's doc comment names what it proves.

## How work gets done here

Feature work follows the SDLC process defined in `.claude/`:

- `.claude/AI_SDLC_README.md` — the end-to-end workflow: starting a feature,
  each phase, closing phases, merging to `main`.
- `.claude/memory.md` — current feature, branch and phase. Read this first when
  picking work back up.
- `CLAUDE.md` — architecture and coding standards. Applies regardless of phase.
- `.claude/git/branching-policy.md` — one branch per feature, named
  `feature/<feature-id>-<slug>`, branched from latest `main`. Direct commits to
  `main` are blocked by a hook.

## Roadmap

**Phase 1 (current)** — frontend only. Bulletins, Mass times, ministries,
parish contact details and news, all read from public parish website content.
Giving and prayer requests link out rather than being built in.

**Phase 2** — a backend may be introduced (Supabase is the candidate) for
capabilities that need one, such as push notifications. Phase 1 code should
stay ready for that without building backend abstractions before they are
needed.
