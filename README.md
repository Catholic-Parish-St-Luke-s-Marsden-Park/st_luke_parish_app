# St Luke's Parish App

A native Android and iOS app for **St Luke's Catholic Parish, Marsden Park** —
Mass times, bulletins, parish news, ministries and contact details on a phone.

The app reads selected **public** content from the parish website
(<https://stlukesmarsdenpark.org.au>), and ministries from the parish API's
public, read-only endpoints (see [Parish API](#parish-api-ministries)). No
private or authenticated parish data is used.

- **Platforms:** Android and iOS only. No web or desktop target.
- **Dart SDK:** `^3.11.0` (any recent Flutter stable).
- **State management:** Riverpod, with providers generated by `riverpod_generator`.

## Current state

This repository is at the **bootstrap slice**. What exists today:

- The app shell — themed `MaterialApp.router`, a 6-destination bottom
  navigation bar, and a side drawer with two more destinations.
- The design system — navy/gold/cream palette, Playfair Display + Source Sans 3
  via `google_fonts`, and 12px card / 20px pill corner radii
  (`lib/core/theme/`).
- Mobile-only responsive helpers for phone vs. tablet widths
  (`lib/core/layout/responsive.dart`).
- Eight placeholder screens, one per navigation destination.

Every feature screen is currently a `PlaceholderScreen` stub. **No feature has
its `domain/` or `data/` layer yet** — no scrapers, parsers, models or
repositories exist. Those arrive one feature at a time, following the process
below.

## Quick start

```bash
flutter pub get
dart run build_runner build --delete-conflicting-outputs   # required: providers are generated
flutter run
```

`build_runner` is not optional — `lib/app/shell/nav_index_provider.dart` relies
on generated output (`.g.dart`), and the app will not compile without it. Use
`dart run build_runner watch --delete-conflicting-outputs` while developing.

### Saint of the Day (Parish API)

The "Saint of the Day" screen loads from the parish API's public
`GET /v1/saints/{date}`, where `{date}` is today's `YYYY-MM-DD` date in Sydney
as computed on the device. No API key or `--dart-define` is needed: the origin
is the same `API_BASE_URL` as the Ministries tab (below). Without a valid
origin the screen shows a "not set up on this build" message and sends no
request. See `.claude/decisions/0008-saint-of-the-day-from-parish-api.md`.

The result is cached on the device for the rest of that Sydney day. If the
server hasn't prepared the day's saint yet (just after midnight), the screen
says so and offers "Try again".

### Parish API (Ministries)

The Ministries tab loads from the parish API (parish_app_service), which parish
staff edit in its `/admin` console. Set the API origin in `assets/app.env`:

```
API_BASE_URL=https://parish-app-service.fly.dev
```

- Origin only, no path. Release builds require `https://`.
- If `API_BASE_URL` is unset, the origin of `BASE_URL` is used instead.
- The app only calls `GET /v1/ministries`, `GET /v1/ministries/{id}` and
  `GET /v1/saints/{date}` (plus `POST /tokens` for push registration).

The last good response is cached on the device and refreshed in the
background; pull down on the tab to refresh by hand. On a first launch with no
network, the app shows `assets/ministries_fallback.json`, a snapshot of
`GET /v1/ministries`. **Refresh it before each release:**

```bash
curl -sS --fail https://parish-app-service.fly.dev/v1/ministries \
  | python3 -m json.tool --indent 2 --no-ensure-ascii > assets/ministries_fallback.json
flutter test test/features/ministries
```

`test/features/ministries/data/ministries_fallback_asset_test.dart` pins the
snapshot's categories and ministries, so it fails when staff have changed them.
Check the diff is expected, then update those expectations.

Checks to run before opening a pull request:

```bash
flutter analyze                    # must report "No issues found!"
dart format .
flutter test
```

## Layout

```
lib/
├── main.dart          entry point: ProviderScope + StLukeApp
├── app/
│   ├── app.dart        MaterialApp.router + theme wiring
│   ├── router.dart     go_router: a single '/' route hosting AppShell
│   └── shell/          bottom nav, side drawer, selected-tab provider
├── core/
│   ├── theme/          palette, typography, shapes, ThemeData
│   └── layout/         phone/tablet breakpoints and page padding
├── features/<feature>/ one folder per feature (see below)
└── shared/widgets/     widgets shared across features
```

Navigation is deliberately shallow: `go_router` owns one route (`/` →
`AppShell`), and the two drawer destinations are pushed with the standard
`Navigator` since neither needs a deep-linkable URL.

Each feature follows a layered split — `presentation/` for UI and its
providers, `domain/` for entities and contracts, `data/` for repositories,
scraper clients and parsers. Only `presentation/` exists so far. The rules that
govern those layers (no network calls in widgets, repositories as the sole
access point for external content, parsers returning typed models) are in
**`CLAUDE.md`** — read it before adding a feature.

## Push notifications

Push notifications use Firebase Cloud Messaging (FCM). The app registers its
FCM token with the parish backend (`https://parish-app-service.fly.dev`, API
docs at `/docs`), which stores it and sends the pushes. The earlier Node.js
`server/` has been retired and is no longer in this repository.

The app registers with `POST /v1/devices`:

```json
{ "fcmToken": "<token>", "platform": "android", "locale": "en-AU" }
```

`platform` is `ios` or `android`. Topics are omitted, so the backend keeps any
it has already stored. The retired server's `/tokens` route is still accepted
by the backend as deprecated, but the app no longer uses it.

Registration behaviour (`lib/core/notifications/notification_service.dart`):

- Failed attempts are retried with linear backoff.
- A `4xx` other than `429` (bad request, App Check) is not retried.
- `429` (rate limited, 20 per 15 min per IP) backs off much longer.
- Failures are logged as the response's stable `code` and `requestId` only,
  never the raw body.

### Prerequisites

- A Firebase project for the app, with `google-services.json` (Android) and
  `GoogleService-Info.plist` (iOS) in place.
- iOS only: an APNs Auth Key (.p8) uploaded under Firebase Console → Project
  Settings → Cloud Messaging, Push Notifications and Background Modes (Remote
  notifications) enabled in Xcode, and a **real device** (simulators are
  unreliable for push).

### Point the app at the backend

Set `API_BASE_URL` in `assets/app.env` to the backend origin only (no path).
The app appends `/v1/devices` itself:

| Where the app runs               | `API_BASE_URL`                                                        |
| -------------------------------- | --------------------------------------------------------------------- |
| Production / release builds      | `https://parish-app-service.fly.dev`                                  |
| Android emulator (local backend) | `http://10.0.2.2:8080`                                                |
| Physical device on Wi-Fi         | `http://<your-PC-LAN-IP>:8080` (allow port 8080 through the firewall) |
| Android device over USB          | `http://localhost:8080` after `adb reverse tcp:8080 tcp:8080`         |
| iOS simulator                    | `http://localhost:8080`                                               |

Release builds require `https://` (plain `http` is rejected).

`assets/app.env` is bundled into the app, so **never put secrets in it**. Do a
full restart (not hot reload) after changing it.

`assets/app.env` is committed with the production URL as the default. If you
point it at a local backend for development, **restore it before building for
release**, then confirm it with:

```bash
RELEASE_CHECK=true flutter test test/release_readiness_test.dart
```

This check is skipped during normal `flutter test` runs and only runs on
request, as a release gate. It fails if `API_BASE_URL` is a loopback/emulator
address or isn't `https`. If a bad URL slips into a release build,
`NotificationService` no-ops token registration with no visible error
(`debugPrint` is a no-op in release builds), so no device ever registers and
no push ever arrives.

### Test a notification

1. Run the app against a backend and accept the notification permission.
2. Confirm the device registered (check the backend's logs or device store).
3. Send a push using the backend's own tooling (see its `/docs`).
4. Test all three app states, since they take different code paths:
   **foreground**, **background** (press Home first) and **terminated**
   (swipe the app away). Each push should appear exactly once. Tapping a
   notification only opens the app for now, with no deep-link routing yet.

Android receives data-only, high-priority messages and the app posts the
notification itself; iOS gets a visible APNs alert, because iOS drops or
throttles data-only pushes.

### Troubleshooting

| Symptom                                            | Likely cause and fix                                                                                                                                  |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Connection refused` on registration               | `localhost` on the device points at the device itself. Use `10.0.2.2` (emulator), `adb reverse`, or the PC's LAN IP; make sure the backend is running |
| `Cleartext HTTP traffic not permitted`             | Android blocks plain `http` to non-localhost hosts. Use `adb reverse` or an `https` URL                                                               |
| Registration fails with a `4xx`                    | Not retried. Check the logged `code` and `requestId` against the backend; a bad request body or App Check failure won't succeed on retry              |
| Registration fails with `429`                      | Rate limited (20 per 15 min per IP). The app backs off and retries; wait and try again                                                                |
| No registration and no logs in a release build     | `API_BASE_URL` missing, malformed or not `https`. Run the release check above                                                                         |
| iOS: no token / `APNs token unavailable`           | APNs key not uploaded to Firebase, Push Notifications capability missing, or running on a simulator                                                   |
| Emulator crash `SIGILL` in `libwebviewchromium.so` | Emulator WebView bug, unrelated to notifications. Update WebView, cold boot the emulator, or test on a real device                                    |

## Testing

`test/` mirrors `lib/`. The suite currently covers the themed shell,
bottom-navigation behaviour including lazy tab building and `IndexedStack`
state preservation, drawer navigation, the generated nav-index provider, and
absence of layout overflow at small-phone, phone and tablet sizes.

Tests trace to requirement IDs (`REQ-F01-002` and similar) recorded with the
feature that introduced them, so a test's doc comment names what it proves.

## How work gets done here

Feature work follows the SDLC process defined in `.claude/`:

- `.claude/AI_SDLC_README.md` — the end-to-end workflow: starting a feature,
  each phase, closing phases, merging to `main`.
- `.claude/memory.md` — current feature, branch and phase. Read this first when
  picking work back up.
- `CLAUDE.md` — architecture and coding standards. Applies regardless of phase.
- `.claude/git/branching-policy.md` — one branch per feature, named
  `feature/<feature-id>-<slug>`, branched from latest `main`. Direct commits to
  `main` are blocked by a hook.

## Roadmap

**Phase 1 (current)** — frontend only. Bulletins, Mass times, ministries,
parish contact details and news, all read from public parish website content.
Giving and prayer requests link out rather than being built in.

**Phase 2** — a backend may be introduced (Supabase is the candidate) for
capabilities that need one, such as push notifications. Phase 1 code should
stay ready for that without building backend abstractions before they are
needed.
