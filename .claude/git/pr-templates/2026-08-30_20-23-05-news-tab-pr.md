- Feature ID: 05
- Feature Name: news-tab

## Summary
- Scope: Replaces the News bottom-nav tab's `PlaceholderScreen` stub with real content (`lib/features/news/`):
  - **"Latest Bulletins" section** — live-fetched via RSS (`https://stlukesmarsdenpark.org.au/category/bulletins/feed/`), parsed with a regex+fallback-chain approach documented in ADR-0004 (a deliberate, well-justified deviation from CLAUDE.md's CSS-selector-first default — see Artifacts), newest-first (explicit descending-`pubDate` sort, not blind feed-order trust), capped at 6 items, LATEST/PREVIOUS labeling, full loading/success/empty/parsing-failure/network-failure UI states.
  - **"Parish News" section** — 2 static announcements from typed config, no scraping.
  - **"Prayer Intentions" section** — static quote/body plus a "Submit Prayer Request ↗" external CTA.
  - New core additions: `lib/core/network/http_client_provider.dart` (shared `http.Client` provider), `lib/core/constants/external_links.dart` additions (`bulletinsFeed`, `bulletinsArchive`, `prayerRequests`).
  - New dependencies: `http: ^1.2.2`, `xml: ^6.5.0`.
  - This feature is the app's first to make its own raw `http` network call for a tab's *primary* content, rather than delegating all network access to a WebView (Donate).
- User value: Turns the News tab from a stub into a live source of parish bulletins and announcements, with a direct path to submitting prayer requests.

## RISKS — RISK-005 fixed by this PR (please read first)

**RISK-005: RESOLVED by this PR.** The release-build Android manifest (`android/app/src/main/AndroidManifest.xml` — the manifest actually merged into release builds) was missing `android.permission.INTERNET`. Because this feature is the app's first to make its own raw `http` call for a tab's primary content, this gap would have broken the entire "Latest Bulletins" section — not an ancillary WebView — for every production Android user, in addition to the pre-existing Donate-tab impact. Fixed with a single manifest line (commit `e1e0081`):
```xml
<uses-permission android:name="android.permission.INTERNET"/>
```
Independently verified in a **real built release APK**, not just the source XML: `flutter build apk --release` succeeded (53.2MB), then `aapt dump permissions` on the built APK confirmed `android.permission.INTERNET` is genuinely present in the shipped manifest. `flutter analyze`/`dart format . --set-exit-if-changed`/`flutter test` re-run clean after the change (175/175, no regressions). Marked Resolved in `.claude/risks/active-risks.md`. The user explicitly chose "fix now" over the prior 03-multi-pages/04-masses-tab ship-and-track precedent, given the severity for this feature's primary content.

**RISK-003 / RISK-004 (pre-existing, from 02-parish-tab/03-multi-pages, scope extended by this feature — not re-litigated):**
- **RISK-003** (GitHub issue #12) — `android/app/src/main/AndroidManifest.xml` still has only a `PROCESS_TEXT` `<queries>` block, no browsable `VIEW`/`tel`/`mailto` intent declarations. This feature adds 3 new `https:`-scheme tap targets that would be affected if this ships unresolved: the bulletin "Download PDF ↗" link, the bulletins-archive fallback link on empty/error states, and the "Submit Prayer Request ↗" CTA — all confirmed via `grep` to route through the same `UrlLauncherService`/`https:` scheme only, no new scheme type. Same root cause and fix already tracked for 02/03/04's links; surface area grows to 12 tap targets total across 4 features. Not touched or worsened by this feature's own commits (`git diff --stat main...feature/05-news-tab -- android/` is empty for RISK-003's file).
- **RISK-004** — `ios/Runner/Info.plist` still has no `LSApplicationQueriesSchemes` key. Notably, this feature's own Visualiser phase live-tested all 3 new tap targets on iOS Simulator and the user explicitly confirmed all worked end-to-end — the strongest on-device evidence any feature has produced for this risk category so far, though it does not fully close RISK-004 project-wide (plain `https` links typically don't require `LSApplicationQueriesSchemes` on iOS in the first place, which is why this is lower-priority than RISK-003/RISK-005 were). Not touched or worsened by this feature's own commits.

**RISK-007 (new, logged this feature's verifier phase — test-infrastructure gap, not a functional defect):**
- The 2 live RSS integration tests (`test/features/news/data/datasources/bulletins_feed_live_test.dart`) make real network calls with no `@Tags`/`skip:`/connectivity guard, and this repo has no `dart_test.yaml` tagging convention to exclude them from a routine `flutter test` run. If `flutter test` is ever run in a fully offline/sandboxed CI environment, these 2 tests would report as failures indistinguishable from a real regression. Has not manifested in any session to date (every run has had network access; both live tests passed again in this session's independent re-run). Recommended fix (introducing this repo's first `dart_test.yaml` tag convention) is a project-wide test-infrastructure decision, out of scope for this feature's own code.

Reviewers: the practical highlight for this PR is that RISK-005 is now fully resolved and independently verified in a release build — no action needed there. RISK-003/004/007 are informational continuity items consistent with prior PRs, no new decision required.
