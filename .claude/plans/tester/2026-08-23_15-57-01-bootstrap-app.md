## Scope
This is a UI-shell-only slice with no data/domain/network layer. Per root `CLAUDE.md` "Coverage expectations," the loading/parsing-failure/network-failure/missing-selector/invalid-url states do not apply here — there is nothing that loads external or async data yet. Testing is scoped to what is actually present: theme tokens, app shell (bottom nav + IndexedStack + side drawer), 8 placeholder screens, the one `riverpod_generator` provider (`selectedNavIndexProvider`), responsive layout helper, and tooling (`flutter analyze` / `dart format`).

## Test Design (derived from BA acceptance criteria, not guesswork)

### REQ-F01-001 — Themed shell (navy/gold/cream, fonts, radii); app builds/runs on Android/iOS
- Widget test: pump `StLukeApp` under `ProviderScope`, assert `ThemeData.scaffoldBackgroundColor == AppColors.cream`, `appBarTheme.backgroundColor`/`navigationBarTheme.backgroundColor == AppColors.primaryNavy`, `colorScheme.primary/secondary` match navy/gold, no exceptions.
- Unit assertions: `AppShapes.cardRadius == 12.0`, `AppShapes.pillRadius == 20.0`.
- Mechanical build/run verification: `flutter build ios --simulator --debug` (succeeded), then installed and launched on a booted iOS 26.2 simulator (`iPhone 16e`) via `xcrun simctl install`/`launch`, captured a screenshot confirming the navy/gold/cream palette, Playfair Display headline font, and correct bottom-nav icon/label rendering live on-device.
- Not covered: an actual Android build/run (no Android emulator/SDK exercised in this sandbox session) and Playfair Display / Source Sans 3 glyph-level font rendering inside `flutter test`'s headless test font environment (widget tests assert theme wiring, not literal glyph shapes). Flagged as a gap below.

### REQ-F01-002 — Bottom nav: exactly 6 destinations, correct icons/labels; IndexedStack preserves tab state
- Widget test: assert `bottomNavDestinations.length == 6`, assert the rendered `NavigationBar.destinations.length == 6`, assert each of the 6 expected labels (Parish/Masses/News/Ministries/Contact/Donate) is present as a descendant of the `NavigationBar`, assert the icon set matches exactly.
- Widget test: tap a destination, assert `selectedNavIndexProvider` (read via an `UncontrolledProviderScope`-injected `ProviderContainer`) updates to the tapped index and the visible screen title updates.
- Widget test: visit tabs 0 -> 1 -> 2 in sequence, assert via `find.byType(<ScreenWidget>, skipOffstage: false)` that previously visited tabs' screen widgets remain present in the tree (inside `IndexedStack`, offstage) rather than being disposed, and that a never-visited tab (index 3, Ministries) is not yet built — proving both the lazy-build and preserve-on-switch behavior described in the BA/coder plan.

### REQ-F01-003 — Side drawer: exactly 2 entries (Resources, Prayer Request)
- Widget test: open the drawer via `ScaffoldState.openDrawer()`, assert exactly one `Drawer`, exactly 2 `ListTile`s, and that "Resources" / "Prayer Request" each appear exactly once as descendants of the `Drawer`.
- Widget test: tap "Resources", assert navigation pushes to a screen whose `AppBar` title is "Resources" (distinct route reachable from the drawer).

### REQ-F01-004 — 8 distinct placeholder screens, no build errors, no real feature data
- Widget test (parameterized over all 8 screens: Parish, Masses, News, Ministries, Contact, Donate, Resources, PrayerRequest): pump each screen standalone, assert no exception is thrown, assert its own title text and icon render.
- Unit test: assert all 8 titles are pairwise distinct.
- Source review (manual, not automated): confirmed by reading each of the 8 screen files that none reference `data`/`domain` layers, network calls, or any live/fetched values — each is a thin wrapper around the shared `PlaceholderScreen` with a static title/icon only.

### REQ-F01-005 — `ProviderScope` wired at root; generated provider drives shell state
- Unit test (`ProviderContainer`, no widget tree): `selectedNavIndexProvider` starts at `0`; calling `.notifier.select(4)` updates state to `4`.
- Widget test: confirms the same provider, read through the widget tree via tap interaction (see REQ-F01-002 tap test), drives the actually-rendered selected tab.
- Source review: `main.dart` wraps `StLukeApp` in `ProviderScope`; `nav_index_provider.g.dart` is `riverpod_generator` output (`@ProviderFor(SelectedNavIndex)`), confirming the provider is generated, not hand-written.

### REQ-F01-006 — No overflow/clipping across phone and tablet sizes
- Widget test: pump full `StLukeApp` at 3 sizes (`360x690` small phone, `390x844` phone, `1024x1366` tablet) via `tester.view.physicalSize`/`devicePixelRatio` overrides; assert `tester.takeException()` is `null` at each size (this catches `RenderFlex overflowed` and other layout-exception classes that Flutter's test binding surfaces as exceptions).
- Widget test: repeat with the side drawer opened, at phone and tablet sizes, asserting no overflow exceptions.
- Not covered: pixel-level clipping that doesn't throw a Flutter layout exception (e.g. silently truncated/clipped content that fits within bounds without an overflow error) is not caught by this method; only exception-raising overflow is detected. Golden-image tests would be needed for that, and none exist yet — flagged as a gap below.

## Unresolved Coverage Gaps (flagged, not silently dropped)
1. **REQ-F01-001 — Android build/run not exercised.** Only iOS was built, installed, and visually verified via simulator in this sandbox. No Android emulator/SDK was exercised. Recommend running `flutter build apk` / `flutter run -d <android-emulator>` before merge, or accepting iOS verification as sufficient proxy given identical Flutter widget tree across platforms — this is a judgment call for the user/Verifier.
2. **REQ-F01-001 — Font glyph verification is theme-wiring-only.** Widget tests assert that `GoogleFonts.playfairDisplay`/`sourceSans3` are wired into the theme, not that the actual glyphs render correctly (Flutter's test font is a fallback test font). The live iOS screenshot does show the intended serif display font rendering correctly, which is stronger evidence than the widget test alone.
3. **REQ-F01-006 — Clipping without exceptions is undetected.** The overflow check only catches Flutter's `RenderFlex overflowed`-style layout exceptions; silent visual clipping that fits within bounds without throwing is not caught. No golden-image tests exist for this feature. Root `CLAUDE.md` lists golden tests as a required test type "for stable, important UI states" — this shell is still expected to change (BA/coder risk notes), so golden tests were judged premature for this bootstrap slice, but this is a real gap if the user wants stronger visual regression coverage now.
4. **No Android tablet / physical-device size check.** REQ-F01-006 tablet coverage is via widget-test `MediaQuery`/view-size overrides only (1024x1366), not a real tablet emulator or device.
5. **Live iOS visual check was a single static screenshot of the default tab only** (Parish, drawer closed). Did not screenshot every tab, the opened drawer, or tablet-simulator sizes live on-device — those states are covered only by widget tests, not visual confirmation on a real rendering engine.
