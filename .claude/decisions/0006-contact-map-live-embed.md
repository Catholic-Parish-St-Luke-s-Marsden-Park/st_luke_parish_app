- **Decision ID:** ADR-0006
- **Title:** Contact tab's map preview becomes a live embedded Google Map, reversing REQ-F03-015/016's "no embedded map SDK" decision
- **Feature:** 03-multi-pages (reopened off the SDLC pipeline, same quick-fix branch as `fix/donate-nav-pulse`)
- **Date:** 2026-10-08
- **Status:** accepted
- **Context:** 03-multi-pages's approved BA plan explicitly specified REQ-F03-015/016 as a *static* map-preview card plus an "Open in Google Maps" button, both handing off to the external Google Maps app/browser — deliberately "no embedded interactive map SDK" (asserted directly by a dedicated widget test: `find.byIcon(Icons.location_on_rounded)` present, no `GoogleMap`-style widget). The user later asked to match the parish PWA's own Contact page instead, which embeds a live, pannable-looking (though actually non-interactive, see below) Google Map via `<iframe src="https://maps.google.com/maps?q=...&output=embed">` inside a `.map-wrap` div (`pointer-events: none` in its CSS). The first implementation attempt loaded that same `output=embed` URL directly via `WebViewController.loadRequest` (reusing `SimpleWebViewScreen`'s existing `url` path, as already used for Donate) and failed in a real build: Google's `output=embed` endpoint checks server-side that the request genuinely originates from inside an `<iframe>`, and refuses direct top-level loads with the literal page text "The Google Maps Embed API must be used in an iframe." — confirmed live by the user on an Android emulator.
- **Decision:** Keep the embedded map (don't fall back to the old static card), but load it correctly: `SimpleWebViewScreen` gained a second, mutually-exclusive constructor parameter, `html` (loaded via `WebViewController.loadHtmlString`), alongside the existing `url` (`loadRequest`). The Contact tab now loads a small local HTML wrapper document containing a genuine `<iframe src="...output=embed">`, mirroring the PWA's own markup exactly (including `allowfullscreen`, `loading="lazy"`, `referrerpolicy="no-referrer-when-downgrade"`). The map preview is wrapped in `IgnorePointer`, matching the PWA's `.map-wrap { pointer-events: none; }` — it's a live visual, not a pannable widget; tapping it (or the unchanged "Open in Google Maps" pill) still hands off to the real external Google Maps app/browser via the existing `UrlLauncherService`. `contact_screen_test.dart`'s REQ-F03-015/016 test group was rewritten to assert the new behavior (an embedded `SimpleWebViewScreen`/`WebViewWidget` whose `html` contains the iframe'd embed URL, wrapped in an `ignoring: true` `IgnorePointer`) in place of the old "no map SDK present" assertion.
- **Alternatives Considered:**
  - Keep the static card, decline the scope change — rejected by the user; PWA parity was the explicit goal.
  - Use `google_maps_flutter` (the real native Maps SDK) instead of a WebView embed — rejected for this quick fix: needs a provisioned Google Maps API key for both Android and iOS plus Cloud Console billing, a materially bigger integration than reusing the WebView infrastructure Donate already proved out, for a preview card that's intentionally non-interactive anyway.
  - Load the embed URL directly via `url`/`loadRequest` (the first attempt) — doesn't work; Google's server-side iframe check refuses it outside a real nested browsing context.
- **Consequences:** REQ-F03-015/016 as originally written no longer describes the shipped behavior; this ADR is the record of why and when that changed. `SimpleWebViewScreen` is now a slightly broader reusable primitive (`url` *or* `html`), which may be useful for any future embed-style content with the same "must be nested" constraint. No Google Maps API key, billing, or native SDK dependency was introduced.
