## Feature Summary
Bootstrap the visual and navigational shell of `st_luke_parish_app`: app-level theme (colors, typography, shapes), a `go_router`-based single shell route hosting an `IndexedStack` app shell with bottom navigation and a side drawer, one placeholder screen per nav destination, app-level Riverpod wiring, and baseline responsive layout scaffolding. This is a thin vertical slice that proves the shell/nav/theme pattern end-to-end — it deliberately contains no real feature data, scraping, or domain logic.

## In Scope
- `lib/core/theme/`
  - `app_colors.dart` — navy/gold/cream palette (matched to `st_luke_frontend_app`, adjusted only if a distinct identity is later required)
  - `app_typography.dart` — Playfair Display + Source Sans 3 via `google_fonts`
  - `app_shapes.dart` — 12px card radius, 20px pill radius
  - `app_theme.dart` — `ThemeData` assembly from the above
- `lib/app/`
  - `app.dart` — `MaterialApp.router` + theme wiring
  - `router.dart` — `go_router` with a single route hosting the app shell
- `lib/app/shell/`
  - `app_shell.dart` — `IndexedStack`-based shell, lazy tab build on first visit
  - `bottom_nav.dart` — 6 destinations: Parish, Masses, News, Ministries, Contact, Donate
  - `side_drawer.dart` — 2 items: Resources, Prayer Request
- 8 placeholder screens (one per nav destination above) — minimal stub content (e.g. centered title/icon), no `data`/`domain` layers, no network or scraping calls
- Riverpod setup: `ProviderScope` bootstrap in `main.dart`; `riverpod_generator`/`riverpod_annotation` wired via `build_runner`; one simple app-level generated provider (e.g. selected nav index) as a working example
- Responsive layout scaffolding: safe-area handling, adaptive padding/sizing for phone vs. tablet widths (mobile-only per root `CLAUDE.md` — no web breakpoints)
- `pubspec.yaml` additions needed for the shell: `flutter_riverpod`, `riverpod_generator`, `riverpod_annotation`, `go_router`, `google_fonts`, `build_runner`, `dev_dependencies` equivalents as needed

## Out of Scope
- Real feature data/domain/repository/parser/scraper logic for any destination (bulletins, events, ministries, contact, donate, roster, resources, prayer_request)
- Webview integration (e.g. Donate, Prayer Request embeds)
- Supabase or any Phase 2 backend concerns
- Tests beyond what the Tester phase will add
- App icon, splash screen, or branding assets beyond what's needed to prove the theme visually

## Assumptions
- `st_luke_parish_app` reuses the same visual identity as `st_luke_frontend_app` (palette, fonts, shapes) unless the user requests a distinct identity later
- The 8 nav destinations and the bottom-nav (6) / drawer (2) split carry over unchanged from `st_luke_frontend_app`
- Placeholder screens are intentionally empty/stub (e.g. centered title text) with no live data, matching the "do not build feature details yet" instruction

- Bottom nav item count (6) plus drawer (2) was carried over from `st_luke_frontend_app`'s current feature set; if parish app's final feature list differs, nav destinations will need to change later
