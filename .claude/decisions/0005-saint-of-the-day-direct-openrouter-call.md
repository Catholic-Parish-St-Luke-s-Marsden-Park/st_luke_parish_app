- **Decision ID:** ADR-0005
- **Title:** Call OpenRouter directly from the client for Saint of the Day, with an interim on-device cache and a hand-rolled Sydney date key
- **Feature:** 06-saint-of-the-day
- **Date:** 2026-09-01
- **Status:** accepted
- **Context:** The parish's live PWA already has a working "Saint of the Day" feature: a Netlify serverless function (`netlify/functions/saint-of-day.mjs`, in the user's other repo `stlukes-marsden-park-app`) calls OpenRouter's `google/gemini-3.1-flash-lite` model server-side, using a hardcoded API key, and caches the result once per `Australia/Sydney` calendar day in a server-side store (Netlify Blobs) shared by every user. Reusing that existing endpoint from this Flutter app was offered as an alternative during BA — it would mean this app never needs an OpenRouter key at all, and calls to the model stay capped at one per day for every user combined. The user explicitly chose instead to call OpenRouter directly from this app, using the same model/prompt, because Supabase/Firebase (the intended eventual backend for this project) is not yet set up and the team wants the feature working now rather than waiting on that.
- **Decision:** `OpenRouterSaintDatasource` calls `https://openrouter.ai/api/v1/chat/completions` directly from the app with the model/prompt/parameters ported verbatim from the reference Netlify function. The API key is never a literal string in source — it is read once via `String.fromEnvironment('OPENROUTER_API_KEY')`, supplied at build/run time via `--dart-define` (see `README.md`). Because there is no shared backend yet, `SaintOfTheDayRepositoryImpl` checks a local `shared_preferences`-backed cache (`SharedPreferencesSaintOfTheDayCache`) keyed to today's `Australia/Sydney` calendar date before calling OpenRouter, and writes the result back after a successful fetch — mirroring the reference server's "one generation per day" behaviour, but per install rather than shared across all users. The cache is implemented behind a `SaintOfTheDayCache` interface specifically so a future Supabase-backed shared cache can replace it without changing `SaintOfTheDayRepositoryImpl`'s public contract, the domain entity, or any presentation code. Since adding a `timezone`-database package was outside the BA-approved dependency list (`shared_preferences` only), the Sydney calendar date is computed via a small hand-rolled NSW-daylight-saving rule (`lib/features/saint_of_the_day/data/sydney_date.dart`: AEDT/UTC+11 from the first Sunday of October to the first Sunday of April, AEST/UTC+10 otherwise) rather than resolving the real IANA timezone database.
- **Alternatives Considered:**
  - Reusing the existing Netlify function (`GET /api/saint-of-day`), as the earlier unfinished Flutter prototype (`stlukes_flutter/lib/services/api_service.dart`) already does — rejected by explicit user decision for this feature. This remains the safer option for a future revisit: the key never leaves the server, and the daily cache is genuinely shared across every user rather than per-install.
  - Adding a `timezone`-database package (e.g. alongside `flutter_native_timezone`) for a fully correct Australia/Sydney date resolution — rejected as outside this feature's approved scope (only `shared_preferences` was approved as a new dependency); the hand-rolled DST rule is accepted as a documented simplification instead.
- **Consequences:** The OpenRouter API key is compiled into the release app binary. Even though it is never committed to git, a `--dart-define` value is still recoverable from a decompiled release APK/IPA — this is a materially weaker security posture than the Netlify-proxy alternative, accepted knowingly by the user for this feature. Recommended mitigations, to action outside this feature's code: set a spend/usage cap on this OpenRouter key from the OpenRouter dashboard, and treat a Supabase/Firebase-backed proxy as the real long-term fix rather than a nice-to-have. Separately, because the cache is on-device rather than shared, N installs opening the screen on a given day can each trigger their own OpenRouter call that day (up to N calls, versus the reference server's 1) — a real cost-model regression versus the proven implementation, accepted for the same reason. The hand-rolled Sydney DST rule can be off by up to an hour only in the couple of hours immediately around the twice-yearly clock change, which does not affect which calendar day a once-a-day cache key resolves to in practice; if the Australian DST rule itself is ever changed by legislation, `sydney_date.dart` needs updating alongside it. If Supabase/Firebase caching is added later, `SharedPreferencesSaintOfTheDayCache` is the only file that needs replacing.
