## User-confirmed decisions this session (not open questions)
1. **Call OpenRouter directly from this Flutter app**, using the same model (`google/gemini-3.1-flash-lite`) and the same structured prompt as the live Netlify function — explicitly chosen over reusing the existing Netlify function endpoint (which was offered as the more secure, zero-client-key alternative). This is a deliberate user decision, to be documented via ADR (see Risks).
2. **Supabase/Firebase is not yet set up in this project.** Full server-side shared caching (like the Netlify function's Blobs store) is not available yet. For now, this feature implements a **local, on-device cache** (per install, not shared across users) keyed to the calendar date in `Australia/Sydney`, mirroring the Netlify function's day-rollover behaviour at the individual-device level. The cache is built behind a repository-level abstraction specifically so a future Supabase-backed shared cache can replace the local one later without changing the domain/presentation layers — "provision to cache," per the user's explicit instruction, means this abstraction boundary, not a Supabase integration in this feature.
4. **Pill styling/position, confirmed:** the existing "Saint of the Day" AppBar pill already sits directly beside "Ask Luke" (`SaintOfTheDayPill(), SizedBox(width: 8), AskLukePill()` in `app_shell.dart`) — no position change needed. It should render with a solid yellow/gold fill instead of the default translucent-white pill style, matching this app's existing `filledButtonTheme` precedent (`backgroundColor: AppColors.gold`, `foregroundColor: AppColors.textPrimary`) rather than an arbitrary new yellow — same gold used for "LATEST" pill and Ministries/Masses accent text elsewhere in the app, keeping the existing sparkle icon and label text unchanged.

3. **API key handling:** per root `CLAUDE.md`'s explicit "do not hardcode secrets, tokens, or credentials in source code" rule, the OpenRouter key is **not** written into any `.dart` file or committed config. It is supplied at build/run time via Flutter's built-in compile-time environment mechanism (`String.fromEnvironment('OPENROUTER_API_KEY')`, set via `--dart-define` or `--dart-define-from-file`), which needs no new package. This keeps the key out of git and out of the BA/coder review diff. **This is a mitigation, not a full fix — see Risks: a `dart-define` value is still compiled into the release binary and is recoverable from a decompiled APK/IPA.** The user already holds a working key (from the Netlify function above) to use locally for this.

## Feature Summary
Replace the "Saint of the Day" AppBar pill's hardcoded "coming soon" dialog with a real feature: tapping it opens a full-screen page showing today's Catholic saint, sourced by calling OpenRouter's `google/gemini-3.1-flash-lite` model directly from the app, using the same prompt structure already proven in the parish's live Netlify function. The result is parsed into 8 labelled fields (name, feast day, born/died, about, famous saying, did-you-know, patron of, prayer) and cached on-device for the current Sydney-local calendar day so the model is not re-called every time the screen is opened. This is a thin vertical slice for this one pill/feature only; no other tab, and no Supabase/Firebase integration, is touched.

## Risks
- **Client-side API key exposure (primary risk of this feature, accepted by explicit user decision).** Even sourced via `--dart-define` and kept out of source control, the key is compiled into the release app binary and is recoverable by anyone who decompiles the APK/IPA or inspects network traffic — a `dart-define` value is not a real secret at runtime, only at rest in git. This is a materially different risk profile than the Netlify-proxy alternative (where the key never leaves the server) that was offered and explicitly declined this session. **Recommended mitigations, for the user to action outside this feature's code:** set a spend/usage cap on this OpenRouter key from the OpenRouter dashboard, and treat a Supabase/Firebase-backed proxy (already the longer-term plan) as the real fix rather than a nice-to-have. This must be documented via ADR per the Decisions above, not silently shipped.
- **On-device-only cache is per-install, not shared.** Unlike the Netlify function's shared server-side cache (one generation per day for every user), each install of this app will independently trigger its own OpenRouter call the first time it opens the screen each day — N installs opening the screen on a given day means up to N model calls that day, not 1. This directly affects API cost and is the main reason Supabase/Firebase is the intended eventual fix; acceptable for now per explicit user instruction, but worth surfacing since it changes the cost model from the proven reference implementation.
- **First feature in this app to add local persistence** (`shared_preferences`). CLAUDE.md's default is "do not add local persistence until there's a clear requirement" — the requirement here (avoiding an OpenRouter call on every screen open) is clear and explicit, but this is a precedent-setting deviation worth flagging, same class of note as feature 05's RSS-vs-CSS-selector ADR.
- **Model output is not guaranteed to match the exact section-header format the parser expects.** The reference implementation's regex-based parser already handles this gracefully (missing sections default to empty string, only "SAINT NAME" has a fallback default) — this feature ports that same tolerant behaviour rather than assuming a rigid format, but a badly-malformed response (e.g. no recognizable headers at all) should still be tested as an explicit parsing-failure UI state.
- **Second network-capable feature after News (05).** Android's release-build `INTERNET` permission was already fixed for feature 05 and should already cover this feature, but Coder/Tester should explicitly re-confirm it (and check iOS App Transport Security defaults, which allow HTTPS out of the box) rather than assume, since this is a different host (`openrouter.ai` vs the parish's own domain).

## Acceptance Criteria

### Pill / navigation
- `REQ-F06-001` — Tapping the "Saint of the Day" AppBar pill pushes a new full-screen `SaintOfTheDayScreen` via `Navigator`; the "Coming soon." `AlertDialog` is removed.

### Data fetch, prompt & parsing
- `REQ-F06-002` — A datasource under `lib/features/saint_of_the_day/data/datasources/` sends a `POST` to `https://openrouter.ai/api/v1/chat/completions` with `model: "google/gemini-3.1-flash-lite"`, the ported structured prompt (containing today's full date, computed in the `Australia/Sydney` timezone), `max_tokens: 1000`, `temperature: 0.3`, an `Authorization: Bearer <key>` header, and `HTTP-Referer`/`X-Title` headers; no screen, widget, or provider calls `http` or OpenRouter directly.
- `REQ-F06-003` — The API key is read via `String.fromEnvironment('OPENROUTER_API_KEY')` and is not present as a literal string in any `.dart` file; if empty/unset, the datasource/repository surfaces a typed "not configured" failure without sending a request.
- `REQ-F06-004` — The request has a bounded timeout (20s); a timeout or network error is converted into a typed network failure, not an unhandled exception.
- `REQ-F06-005` — A non-2xx response is converted into a typed failure without surfacing raw response/exception text to the UI.
- `REQ-F06-006` — The response body's `choices[0].message.content` text is parsed via a ported version of the reference regex-section extractor, producing `name`, `feast`, `bornDied`, `about`, `saying`, `didYouKnow`, `patronOf`, `prayer`; a missing section yields an empty string for that field (empty string for all except `name`, which defaults to `"Saint of the Day"`), matching the reference implementation's tolerant behaviour.
- `REQ-F06-007` — If the response contains no usable content at all (e.g. empty `choices`), this is a typed parsing/empty failure, not a crash or a blank screen.

### Caching
- `REQ-F06-008` — Before calling OpenRouter, the repository computes today's date key in `Australia/Sydney` and checks the local cache (`shared_preferences`-backed) for an entry under that key; a cache hit returns the cached `SaintOfTheDay` without any network call.
- `REQ-F06-009` — On a cache miss, after a successful fetch+parse, the result is written to the local cache under today's date key, and any previously-cached entry for a different date is cleared (mirroring the reference server's "only ever hold the current day" behaviour).
- `REQ-F06-010` — The cache read/write path is implemented behind an interface (`SaintOfTheDayCache` or equivalent) so it can later be swapped for a Supabase-backed implementation without changing the repository's public contract, domain entity, or presentation layer.

### UI states
- `REQ-F06-011` — The screen explicitly handles and visually distinguishes: loading, success, network failure (with a retry action), parsing/empty failure (with a retry action), and "not configured" (missing API key) — no raw exception text shown to the user in any state.
- `REQ-F06-012` — All interactive elements (retry button, back navigation) meet the 48x48 logical-pixel minimum touch target.
- `REQ-F06-013` — The screen uses plain-text section labels with no icon or emoji glyphs, consistent with Ask Luke/News/Masses (per the Assumptions above; revisit only if the user overrides at review).
- `REQ-F06-014` — Loading/error/empty text uses named `TextTheme` styles (no hardcoded sizes below 12 logical pixels) and reflows rather than overflows at increased system text scale, consistent with `test/app/app_test.dart`'s existing `expectNoOverflowAt` sweep pattern.
