## Feature Summary
Fill in real, static content for the three bottom-nav tabs that currently render only the generic `PlaceholderScreen` stub: **Ministries** (a grid of 16 ministries grouped into 4 categories, each opening a detail screen with a mailto "Join Us" CTA), **Contact** (a tappable list of parish contact details — phone, mobile, email, addresses, office hours, Facebook, website — plus a static map-preview card that opens Google Maps externally), and **Donate** (an in-app WebView loading the parish website's donate page). Ministries and Contact content is authored as static, typed Dart configuration, following the same `domain/entities` + `data/config` + `presentation/screens+widgets` layering already established by the Parish tab (02-parish-tab) — no repositories, providers, or datasources are introduced for these two, since nothing is fetched over the network. Donate is the one genuinely dynamic piece: a thin WebView screen loading a fixed external URL, requiring a new `webview_flutter` dependency.

This is a content-fill slice for 3 of the 6 tabs only. It does not touch navigation/routing structure (already wired), the shared AppBar chrome (already built in 02-parish-tab), or the Masses/News tabs.

## Risks
- **RISK-003/RISK-004 carryover**: 02-parish-tab identified that Android is missing a `<queries>` block (GitHub issue #12) and iOS's `Info.plist` has no confirmed `LSApplicationQueriesSchemes` entry, both of which can cause `url_launcher`'s external-link launches to silently fail on real devices. This feature adds several new external-link launch points (Ministries mailto CTA, Contact tel/mailto/Facebook/website/Google-Maps launches) that are subject to the exact same class of failure. This BA plan does not fix RISK-003/RISK-004 (fixing the manifest is out of scope here, per Out of Scope), but flags that the new launch points inherit the same known risk and should be verified against the same tracked issue during Verifier/Visualiser phases, not treated as a new, separate bug if it reproduces.
- `webview_flutter` is a new dependency with native platform channel/WebView-engine dependencies (Android `android.webkit.WebView`, iOS `WKWebView`); build/runtime behavior should be sanity-checked on both platforms during Coder/Verifier phases (e.g. Android Gradle/minSdk compatibility).
- The donate page URL (`https://stlukesmarsdenpark.org.au/donate/`) is an external page outside this repo's control; if the parish website changes that page's structure or the URL itself moves, only the loaded content changes (the app just displays whatever HTML/JS is at that URL) — no parsing/scraping fragility here since this is a full WebView, not extraction, but the URL itself could go stale and needs occasional confirmation it still resolves.
- Large amount of ported static content (16 ministries with full paragraph copy) increases the chance of a copy/paste/typo drift from the reference app during Coder phase; Coder should diff against the reference file rather than retype by hand where feasible.
- No network connectivity handling is specified beyond the WebView's own load-failure state; a fully offline device will see the WebView's native error page/failure callback, which is treated as the in-scope "network failure" state for Donate (see Acceptance Criteria), not a custom offline banner.
