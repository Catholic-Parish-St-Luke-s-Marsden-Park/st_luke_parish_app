Confirmed via live Android emulator testing during the visualiser phase, not assumed.
2. **REQ-F02-015 structural-only test.** The tester's own test for this REQ is intentionally weak (`expect(true, isTrue)`) and self-documented as such. The verifier independently confirmed the actual requirement (file locations) directly via the filesystem, so the requirement itself is satisfied even though the automated test's contribution to that confidence is minimal. Not a blocking gap, but worth noting for future test-authoring: a `flutter analyze`-style import-lint rule or a checked-in file-location smoke test would be a stronger long-term guard than a tautological assertion.
3. **No live device/emulator run for anything besides the leadership-link bug.** The visualiser phase did run the app live on an Android emulator and did check AppBar width/overflow, section order, and general rendering — the leadership-link bug was the one confirmed defect out of that live pass; the AppBar-width risk flagged by BA/coder/tester was not reported as a problem by the visualiser's live run. Treated as adequately covered for this feature.
4. **iOS not exercised.** Neither the tester nor visualiser phase ran the app on iOS/an iOS simulator. `Info.plist`'s `LSApplicationQueriesSchemes` (the iOS analog of the Android `<queries>` gap) was not checked. This is a real, additional gap beyond what's captured in GitHub issue #12, which is Android-specific. Logged as a new risk below.
5. **Golden/visual regression tests** — none exist yet for this feature's UI, consistent with the same judgment call made in `01-bootstrap-app`'s tester phase (UI still expected to evolve). Not blocking.
6. **Image licensing** (Vatican News, Diocese of Parramatta LinkedIn-sourced images) — not independently re-verified by the verifier; carried forward as a non-blocking, already-flagged risk from the coder phase.

## New Risk Identified During This Phase (beyond #12)

- **iOS external-link launching is unverified.** `Info.plist` was not checked by any phase for `LSApplicationQueriesSchemes` entries, which iOS may require for `canLaunchUrl`-style checks against `http`/`https` schemes depending on the `url_launcher` version's behavior. Given the confirmed Android-side gap stemmed from exactly this class of platform package-visibility configuration, the same class of issue is plausible on iOS and unverified either way (could be already fine as `https` is a system scheme not typically requiring `LSApplicationQueriesSchemes`, but this has not been confirmed by reading `Info.plist` or testing on a simulator/device). Logged as RISK-004 below.

**Rationale:** All 29 BA-approved requirements (REQ-F02-001 through REQ-F02-029, including REQ-F02-016a) have complete, verifiable code evidence and test evidence, and every test was independently re-run and confirmed passing (58/58), with `flutter analyze`/`dart format` clean. Traceability is complete — no requirement is missing evidence. However, REQ-F02-005, REQ-F02-006, and REQ-F02-007 (leadership-entry external-link launching) have a **confirmed, root-caused, live-device defect** (GitHub issue #12: missing `<queries>` block in `android/app/src/main/AndroidManifest.xml`) that widget-test evidence alone does not surface and cannot surface by the tester's own deliberate, reasonable design choice (fake `UrlLauncherService` to avoid platform channels in widget tests). This is precisely the kind of gap between "tests pass" and "feature works for a real user" that a clean pass should not paper over. This mirrors the precedent set by `01-bootstrap-app`'s verifier phase, which also issued a conditional pass for an analogous live-verification gap (RISK-002) that was subsequently resolved via live-device confirmation before full pass.

This is **not a fail**: the defect is narrow (external link tap silently no-ops rather than crashing, affects 3 of 29 requirements, and has a known, low-risk, well-understood fix), the rest of the feature is fully verified, and the fix is a manifest-only change with no `lib/`/`test/` code changes required. A clean pass would be inappropriate because 3 requirements' real-world behavior is confirmed broken; a fail would be disproportionate given how contained and well-understood the gap is, and how much of the feature (26/29 requirements, plus the underlying app-wiring/config-injection pattern for all leadership links) is fully verified and working.

**Conditions for full pass:**
1. Fix the `android/app/src/main/AndroidManifest.xml` `<queries>` block (GitHub issue #12) to include a browsable `http`/`https` intent-filter entry, re-verify live on an Android emulator/device that all 3 leadership-link taps (Pope Leo XIV, Bishop Vincent Long, Fr Gayan Thamel) actually open an external browser, and close issue #12.
2. Check `ios/Runner/Info.plist` for `LSApplicationQueriesSchemes` and verify (via iOS simulator or documentation of `url_launcher`'s `https` scheme behavior) whether an analogous iOS-side gap exists (RISK-004, logged below).

Neither condition requires rework of already-verified requirements or a return to Coder/BA phases — this can proceed to Deployer with these two items tracked as open risks, consistent with how `01-bootstrap-app` handled its own conditional pass (RISK-002 was resolved during the Deployer phase, not by looping back to Coder).
