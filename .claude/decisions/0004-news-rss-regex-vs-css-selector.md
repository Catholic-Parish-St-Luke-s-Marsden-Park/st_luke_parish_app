- **Decision ID:** ADR-0004
- **Title:** Use WordPress RSS feed + regex extraction for bulletins, not CSS-selector scraping of the rendered `/#bulletins` page
- **Feature:** 05-news-tab
- **Date:** 2026-08-30
- **Status:** accepted
- **Context:** Root `CLAUDE.md`'s Scraping Strategy section states CSS selectors are the app's default extraction format, with XPath allowed only "as an exception when CSS selectors cannot reliably express the target." It does not explicitly anticipate a feed+regex mechanism. The News tab needs to show up to 6 bulletin PDF links, newest first, sourced from the parish's public WordPress site. Two mechanisms were available: (1) CSS-selector scraping of the rendered `https://stlukesmarsdenpark.org.au/#bulletins` page, matching CLAUDE.md's literal wording, or (2) fetching the WordPress category RSS feed (`https://stlukesmarsdenpark.org.au/category/bulletins/feed/`) and extracting each bulletin's PDF link via a regex against the feed's `content:encoded`/`description` fields. Option 2 is a proven, working approach already implemented in a sibling reference Flutter app (`st_luke_frontend_app`'s `lib/feed_parsing/rss_bulletin_parser.dart` and `lib/features/bulletins/data/feed_bulletins_repository.dart`) built against this same parish site. Option 1's target page structure (the rendered `/#bulletins` section) had never been inspected or selector-mapped by any prior session — its reliability for exposing PDF `<a href>` links via CSS selectors was unverified and unproven.
- **Decision:** Ported the reference app's RSS+regex approach: fetch `https://stlukesmarsdenpark.org.au/category/bulletins/feed/` via `http`, parse the XML via `xml`, iterate `<item>` elements (capped at 6), and extract each bulletin's PDF link via a case-insensitive regex (`href="([^"]+\.pdf[^"]*)"`) matched against `content:encoded` (falling back to `description`, then to the item's `<link>`). Verified live against the real site during this Coder phase (`curl` with a descriptive `User-Agent`, since the default `curl`/generic UA is rejected with HTTP 403 by the host's WAF — the app's own datasource sends the same `User-Agent` header for this reason) — confirmed the feed returns `<item>`/`content:encoded`/`description`/`pubDate` exactly as assumed, with `pubDate` in RFC 822/1123 format and PDF `<a href>` links present in `content:encoded` for every item observed. This deviates from CLAUDE.md's CSS-selector-first wording in *mechanism* only — the RSS feed is the same public parish content a CSS scrape of the rendered page would read, so the "public content only" rule is fully honored; no admin/private endpoint is used.
- **Alternatives Considered:**
  - CSS-selector scraping of the rendered `/#bulletins` page, per CLAUDE.md's literal default — rejected for this feature: the page's actual DOM structure for exposing PDF links was never inspected or selector-mapped by any prior session, making this the higher-risk, unproven path versus reusing already-working logic against the same site.
  - XPath scraping of the rendered page, per CLAUDE.md's stated "exception" case — rejected: CLAUDE.md frames XPath as an exception specifically for when CSS selectors can't express a target on a page being scraped, not as a substitute mechanism for RSS; doesn't apply here since no page-DOM scraping is happening at all.
- **Consequences:** No CSS-selector-based scraping is added for bulletins in this feature, so `.claude/context/selector-registry.md` does not gain a bulletins entry (per the approved BA plan's explicit note that a selector-registry entry is not applicable to RSS+regex extraction). If the parish's WordPress RSS feed is ever disabled/restructured, bulletins would need a different mechanism (e.g. a future CSS-selector scrape of the rendered page, at that point requiring its own selector-registry entry) — a normal, localized risk under CLAUDE.md's "expect selectors/parsing to break over time; design so updates are easy" guidance, isolated entirely to `data/datasources/` and `data/parsers/` in this feature. The regex is intentionally narrow (`href="...\.pdf..."` only) and could miss a PDF link embedded in an unexpected HTML shape; this is mitigated by the `<link>` fallback (REQ-F05-004) so the tap target is never silently dead.
