## Feature Summary
Add a live "Upcoming Events" section to the News tab, positioned between the hero banner and the existing "Latest Bulletins" section, sourced from the parish website's live AI1EC calendar feed — showing everything the feed returns (not filtered to Masses only). The inline section shows only events falling within the next 7 days; a "View all upcoming events" link below it opens a separate, fully paginated Events screen covering everything further out. Each event row (in both places) shows a date/time pill, title, and optional location, plus two separate tap targets: a "Details" action that opens an in-app sheet with the event's full title, date/time, location, and description — built entirely from fields already parsed from the feed, no external navigation needed — and an "Add to my calendar" action that exports that single event into the user's device calendar. This is the app's third live-network feature (after News' bulletin RSS and Saint of the Day's OpenRouter call) and its first to parse iCalendar (RFC 5545) content rather than RSS/XML — a materially more complex parsing format, particularly around recurring events and timezones, which this plan flags explicitly rather than quietly assuming away. It is also the app's first feature with a pushed sub-screen reached from within a tab rather than only tab/drawer-level navigation (via the already-present `go_router`).

## Risks
- **iCalendar (RFC 5545) parsing is materially more complex than News' RSS+regex approach.** Real hazards: line folding/unfolding, multiple `DTSTART`/`DTEND` value formats, and recurrence rules. Recommend Coder scope the hand-rolled parser narrowly to only the fields this feature needs, but explicitly permit Coder to adopt a mature pub.dev ICS package (e.g. `icalendar_parser`) instead if a live inspection of the real feed shows meaningfully complex structure a narrow hand-rolled parser can't safely cover.
- **Recurring events are confirmed `RRULE` templates** (one `VEVENT` per recurring Mass/group, e.g. "every Saturday"), per the reference PWA's code. That reference implementation only ever computes the *single next* occurrence per template (`rule.after(now, true)`) — sufficient for a "what's coming up right now" widget, but **not sufficient for this feature's own "View all upcoming events" pagination**, which needs genuine window-bounded expansion (e.g. the Sunday after next, and the one after that) so paging forward actually surfaces further real occurrences rather than repeating or omitting them. This is real, scoped extra work beyond what the reference implementation did — Coder implements at minimum `FREQ=WEEKLY`/`DAILY` expansion with `UNTIL`/`COUNT` bounds across the display window, not just "next occurrence".
- **Timezone correctness.** Unlike the Masses tab's hand-authored display strings (no timezone math at all), this feature parses real date-time values from an external feed; a naive parse ignoring `TZID`/UTC-vs-floating distinctions could display event times shifted by hours.
- ~~Per-event detail URL availability~~ — resolved, and now lower-stakes than first scoped: "Details" is an in-app sheet built from fields already parsed from the feed, not an external link, so it no longer depends on the feed reliably providing a per-event URL at all. The URL, when present, is only an optional secondary link inside that sheet.
- **robots.txt disallow-scope interpretation** — this BA phase's own reasonable-effort reading (crawler/indexing-scoped, not a block on a single legitimate client fetch), now meaningfully reinforced by real evidence: the parish's own other app (`stlukes-marsden-park-app`, a Netlify PWA) fetches this exact URL from its own server in production today. Still not a definitive legal/compliance determination for a from-device mobile fetch specifically, so still flagged for the user's explicit sign-off before Coder builds the datasource against this URL.
- **Calendar-export mechanism choice.** `add_2_calendar` (opens the native Calendar app/share-sheet pre-filled with the single event; no calendar read/write permission required; matches this app's current minimal-permissions footprint — only `INTERNET` is declared anywhere today) vs. `device_calendar` (writes directly into a calendar the user selects, but requires requesting calendar permissions on both platforms — a new, more invasive permission class). Recommend `add_2_calendar`; still flagged for explicit confirmation (see Unknowns).
- **Two tap targets per row** ("Details" and "Add to my calendar," per the user's explicit "both shown side-by-side" choice) increases visual density versus the single-action reference screenshot — needs deliberate spacing/layout care so the two targets are each comfortably tappable and visually distinct, especially at larger system text scales.
- **First pushed sub-screen off a tab.** Every existing screen in this app is reached via bottom-nav tab or drawer only; the All Events screen is this app's first screen reached by an in-content link pushing a new route via `go_router`. Low risk (the dependency and routing pattern already exist), but worth Coder/Tester explicitly confirming back-navigation (system back button / app-bar back arrow) returns cleanly to the News tab.
- **Live feed availability/structure drift**, same class of risk as the still-open RISK-007 — this feature's own live integration test(s) should follow whatever convention eventually resolves RISK-007, or else inherit the same gap.
- **No new release-build permission risk expected** — RISK-005 already resolved with a blanket `INTERNET` permission that covers this feature's new HTTP calls; worth Deployer re-confirming per the established pattern.

## Acceptance Criteria

### Events — data fetch & parsing
- `REQ-F08-001` — The app fetches the live parish events feed via the `http` package from a datasource under `lib/features/events/data/datasources/`, with a bounded request timeout and the same custom `User-Agent` convention established by `BulletinsFeedDatasource`; no screen, widget, or provider calls `http` directly.
- `REQ-F08-002` — The feed response is parsed under `lib/features/events/data/parsers/`, extracting `SUMMARY`, `DESCRIPTION`, `LOCATION`, `DTSTART`, `DTEND`, `UID`, and `URL` (when present) for each `VEVENT`, including correct unfolding of RFC 5545 folded continuation lines.
- `REQ-F08-003` — `DTSTART`/`DTEND` values are parsed into typed `DateTime`s. The confirmed common case is `;TZID=Australia/Sydney` floating local time (handled via the "fake UTC" wall-clock technique from Assumptions); the parser also defensively handles date-only, UTC (`Z`-suffixed), and other `TZID`-qualified forms if Coder's own live fetch finds them present too.
- `REQ-F08-004` — A `VEVENT` block that fails to parse is skipped individually (logged, not thrown) rather than failing the entire feed fetch.
- `REQ-F08-005` — The parsed event list is filtered to exclude events whose end (or start, if no end) is in the past, and sorted ascending by `start`.
- `REQ-F08-006` — Recurring events (confirmed `RRULE`-bearing `VEVENT` templates) are expanded into individual displayed occurrences across the full display window needed by both the inline 7-day section and the All Events screen's pagination — at minimum `FREQ=WEEKLY`/`DAILY` with `UNTIL`/`COUNT` support, genuinely producing multiple future occurrences per template (not just the single next one, which the reference PWA's simpler widget uses but which isn't sufficient here).
- `REQ-F08-007` — The calendar-export package selected is added to `pubspec.yaml` as a direct dependency at its latest stable version.

### Events — architecture & failure handling
- `REQ-F08-008` — A `ParishEvent` domain entity is defined as a typed, immutable class under `lib/features/events/domain/entities/`, not a dynamic `Map`.
- `REQ-F08-009` — An abstract `EventsRepository` contract is defined under `lib/features/events/domain/repositories/`; a concrete implementation under `lib/features/events/data/repositories/` is the sole orchestration point for fetch, parse, validate, filter, sort, and map.
- `REQ-F08-010` — Network failures are converted into an explicit typed failure by the repository, not a raw/unhandled exception surfaced to the UI.
- `REQ-F08-011` — A total parsing failure is converted into an explicit typed failure by the repository, distinct from an individually-skipped malformed `VEVENT` per `REQ-F08-004`.
- `REQ-F08-012` — Events are exposed via a Riverpod provider under `lib/features/events/presentation/providers/` (generated via `riverpod_generator`, `.g.dart` committed alongside) as `AsyncValue<List<ParishEvent>>`, `autoDispose`, and this single provider backs both the inline section and the All Events screen.
- `REQ-F08-013` — Screens/widgets read events only through this provider (`ref.watch(...)`), never by importing the repository/datasource/parser directly.

### Events — inline section (News tab) UI states
- `REQ-F08-014` — Loading state: while the provider is loading, the inline Events section shows an explicit, user-friendly loading indicator.
- `REQ-F08-015` — Success state: the inline section renders only events whose `start` falls within the next 7 days (today + 6 days) from the full sorted list, in ascending order, each row showing a date/time pill, bold title, and italic location when present.

- `REQ-F08-019` — Network-failure state: an explicit, user-friendly error message distinguishable in wording from the parsing-failure message where practical, plus the fallback link from `REQ-F08-016`.

### Per-event actions (both inline section and All Events screen)
