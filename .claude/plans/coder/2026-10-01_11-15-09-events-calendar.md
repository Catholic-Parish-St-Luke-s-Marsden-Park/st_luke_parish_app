## Summary of Implementation
Implemented all 39 approved requirements (REQ-F08-001..039): a new `lib/features/events/` module (domain/data/presentation layers) fetching and parsing the live AI1EC iCalendar feed, expanding recurring `RRULE` events via the `rrule` package bounded to a 180-day lookahead, and exposing the result through a single Riverpod provider shared by an inline "Upcoming Events" section (News tab, next 7 days only) and a paginated "All Events" screen. Each row shows a date/time pill, title, optional location, and two separate actions — "Details" (an in-app bottom sheet built entirely from already-parsed feed fields, per the user's explicit request mid-BA) and "Add to my calendar" (`add_2_calendar`, opens the native Calendar app).

### Domain (`lib/features/events/domain/`)
- `entities/parish_event.dart` — immutable `ParishEvent` (uid, title, start/end in "fake UTC", displayTime, isAllDay, location, description, detailUrl).
- `failures/events_failure.dart` — sealed `EventsFailure` with `EventsNetworkFailure`/`EventsParsingFailure`, mirroring `BulletinsFailure` exactly.
- `repositories/events_repository.dart` — abstract `getUpcomingEvents()` contract returning the one full, sorted, future-only list both screens read from.

### Data (`lib/features/events/data/`)
- `datasources/parish_events_feed_datasource.dart` — mirrors `BulletinsFeedDatasource` exactly (10s timeout, same `User-Agent`, typed network failure).
- `parsers/ics_event_parser.dart` — hand-rolled field extraction (unfolding, `SUMMARY`/`DESCRIPTION`/`LOCATION`/`DTSTART`/`DTEND`/`UID`/`URL`/`RRULE`) + `rrule`-package-driven recurrence expansion + the fake-UTC/`timezone`-package hybrid for Sydney-local time (ADR-0006, REQ-F08-003/006). Exposes `sydneyNowAsFakeUtc()`, reused by `EventsSection` for its 7-day windowing (a presentation display-window calculation, not fetch/parse/export logic — see that file's own doc comment).

## Live feed verification (REQ-F08-039c, 2026-10-01)

Fetched the real production feed directly (via an authenticated same-origin
`fetch()` in a browser session, since both a direct HTTPS fetch and the
web-fetch tool are blocked by the site's robots.txt for this endpoint) at
`https://stlukesmarsdenpark.org.au/?plugin=all-in-one-event-calendar&controller=ai1ec_exporter_controller&action=export_events&no_html=true`.

Result: `200 OK`, `Content-Type: text/calendar; charset=utf-8`, 5312 bytes,
9 `VEVENT` blocks. Findings against the parser's assumptions:

- `PRODID` is kigkonsult.se iCalcreator (standard AI1EC backend) — confirms
  this site does run the same plugin/export endpoint the reference PWA
  targets.
- Every current `VEVENT` is `RRULE`-based (weekly or monthly BYDAY, including
  ordinal forms like `BYDAY=2FR`) — none are one-off/non-recurring, and none
  are all-day (`VALUE=DATE`). `DTSTART`/`DTEND` are consistently
  `;TZID=Australia/Sydney` floating-local values — confirms the "fake UTC"
  technique's input shape exactly.
- Several events have **no `DTEND` at all** (e.g. the two `Sunday Mass`
  entries), not just `DTSTART == DTEND`. Already handled: `ParishEvent.end`
  is nullable and `addEventToDeviceCalendar` falls back to
  `event.start.add(Duration(hours: 1))` when absent — no code change needed,
  just confirms that fallback path is live in production data, not only in
  tests.
- `LOCATION`/`DESCRIPTION`/`URL` values use real RFC 5545 line folding
  (`\r\n ` continuation) and backslash-escaped commas
  (`...Marsden Park NSW 27\r\n 65\,...`) — confirms `_unfoldIcs`/
  `_unescapeIcsText` are exercised correctly against real bytes, not just
  the hand-written test fixtures.
- Unrecognised fields present in real events and correctly ignored by the
  parser's field-scoped extraction: `CATEGORIES`, `CONTACT`, `DTSTAMP`,
  `SEQUENCE`, `GEO`, `X-COST-TYPE`, `X-WP-IMAGES-URL`, `X-ALT-DESC`,
  `X-INSTANT-EVENT`.
- `UID` values are not always a simple slug (one is
  `ai1ec-36@parish.parracatholic.org/stlukesmarsdenpark`, containing a `/`)
  — harmless, since `UID` is only ever used as an opaque string for the
  dedup key, never parsed.
- The `VTIMEZONE` block's nested `BEGIN:STANDARD`/`BEGIN:DAYLIGHT`
  sub-blocks do not collide with the `BEGIN:VEVENT` block scanner.

No parser changes were required — this was a verification-only pass, and it
passed against real bytes, not just the hand-written fixtures in
`ics_event_parser_test.dart`. One residual gap: the current feed happens to
contain no non-recurring, single-occurrence `VEVENT` (every entry is
`RRULE`-based) and no all-day event, so those two code paths remain
verified only by the unit tests, not by live data — acceptable, since both
are handled per RFC 5545 generically rather than special-cased to this
feed's current content.
