## Open Risks

- **Risk ID:** RISK-003
- **Title:** Leadership-entry external links (Pope Leo XIV, Bishop Vincent Long, Fr Gayan Thamel) silently fail to launch on real Android devices — missing AndroidManifest `<queries>` block
- **Feature:** 02-parish-tab (scope re-confirmed and extended by 03-multi-pages's verifier phase; now further extended by 05-news-tab's verifier phase)
- **Impact:** High for user-facing correctness of REQ-F02-005/006/007. Tapping any of the 3 tappable Church Leadership entries produces no visible effect on a real Android device/emulator (confirmed live on `emulator-5554`, API 36) even though the corresponding widget tests pass. Root cause: `android/app/src/main/AndroidManifest.xml` has no `<queries>` entry for a browsable `http`/`https` `VIEW` intent, so on Android 11+ (API 30+) package-visibility rules cause `url_launcher`'s `canLaunchUrl` (called at `lib/core/services/url_launcher_service.dart:24`) to return `false` for every browser package, and `launchExternal` silently returns `false` without ever calling `launchUrl` — no exception, no crash, no visible feedback to the user. Widget-test evidence for REQ-F02-005/006/007 (`test/features/parish/parish_screen_test.dart`) cannot catch this by design, since those tests inject a fake `UrlLauncherService` via `urlLauncherServiceProvider.overrideWithValue(...)` specifically to avoid touching platform channels — a reasonable test-design choice that nonetheless leaves this exact class of platform-configuration bug undetectable by any current automated test.
  - **Addendum (03-multi-pages verifier phase, 2026-08-27):** Re-read `android/app/src/main/AndroidManifest.xml` directly — still unchanged, still only a `PROCESS_TEXT` `<queries>` entry. This feature (03-multi-pages) adds this app's first `tel:`/`mailto:` launches (Ministries "Join Us" CTA is `mailto:`; Contact Phone/Mobile are `tel:`, Email is `mailto:`) in addition to more `https:` launches (Contact Facebook/Website/Google-Maps). The originally-suggested fix (a `<queries>` block scoped only to `action=VIEW, category=BROWSABLE, data scheme="https"`) covers the `https:` launches but would **not** necessarily cover `tel:`/`mailto:` intent resolution — those need their own scheme entries (or an `ACTION_DIAL`/`ACTION_SENDTO` `<queries>` entry) to be reliably resolvable by `canLaunchUrl` on Android 11+. The eventual manifest fix should cover all three schemes this app now uses (`https`, `tel`, `mailto`), not just `https`.
  - **Addendum (05-news-tab verifier phase, 2026-08-30):** Independently re-read `android/app/src/main/AndroidManifest.xml` this session (`git diff --stat d4ec7f0..6da5057 -- android/ ios/` shows no changes in this feature's commit range) — still unchanged, still only the `PROCESS_TEXT` `<queries>` entry. This feature adds 3 more `https:`-scheme external-link tap targets, all routed through the same `UrlLauncherService`/`canLaunchUrl` mechanism: the bulletin "Download PDF ↗" link (`lib/features/news/presentation/widgets/bulletin_list_tile.dart:71-73`), the bulletins-archive fallback link shown on the empty/error states (`lib/features/news/presentation/widgets/bulletins_message_view.dart:32-34`), and the "Submit Prayer Request ↗" CTA (`lib/features/news/presentation/widgets/prayer_intentions_section.dart:44-46`). No new risk class — same root cause, same manifest fix — but the surface area affected by the underlying bug (if unresolved) and by the eventual fix's verification checklist grows from 9 tap targets (02+03) to 12.
- **Likelihood:** Certain — already reproduced live (before/after screenshots identical, `adb logcat` shows no exception around the tap).
- **Mitigation:** Add a browsable-intent `<queries>` block to `android/app/src/main/AndroidManifest.xml` covering `https`, `tel`, and `mailto` schemes (an `<intent>` with `android.intent.action.VIEW` + `category.BROWSABLE` + `<data android:scheme="https"/>`, plus equivalent entries/`ACTION_DIAL`/`ACTION_SENDTO` coverage for `tel:`/`mailto:`), then re-verify live on an Android emulator/device that all affected taps (leadership links, Ministries "Join Us" CTA, Contact Phone/Mobile/Email/Facebook/Website/Maps, and now News' Download PDF/bulletins-fallback/Submit Prayer Request links) work. Tracked as GitHub issue #12 (https://github.com/Catholic-Parish-St-Luke-s-Marsden-Park/st_luke_parish_app/issues/12), filed by the App-Visualiser phase with root cause and suggested fix included (scope should be expanded to cover `tel`/`mailto` per the 03-multi-pages addendum). This is a manifest-only fix; no `lib/`/`test/` code changes are required.
- **Owner:** Deployer (or a targeted Coder follow-up before merge, at the user's discretion)
- **Status:** open

- **Risk ID:** RISK-005
- **Title:** Release-build Android manifest is missing `android.permission.INTERNET` — the Donate WebView and News' bulletin RSS fetch will both fail in production
- **Feature:** 03-multi-pages (now directly extended by 05-news-tab's verifier phase)
- **Impact:** High. Independently read all three Android manifest variants this session: `android/app/src/debug/AndroidManifest.xml` and `android/app/src/profile/AndroidManifest.xml` both declare `<uses-permission android:name="android.permission.INTERNET"/>` (explicitly commented as being for Flutter tooling/hot-reload — a dev-only concern), but `android/app/src/main/AndroidManifest.xml` — the manifest merged into **release** builds — has no `INTERNET` permission at all, and `android/app/build.gradle.kts` has no manifest-merger override that would add one. `webview_flutter`'s underlying `android.webkit.WebView` (used by the Donate tab, `lib/shared/webview/simple_webview_screen.dart`) requires `INTERNET` to make any network request. A release APK/AAB of this app would be unable to load `https://stlukesmarsdenpark.org.au/donate/` at all — every production user would see the "Unable to load this page" error state (`SimpleWebViewScreen`'s `_WebViewErrorState`) permanently on the Donate tab. This is a release-build-only failure mode: it did not reproduce during any prior phase's testing or any visualiser's live "everything looks good" run, because `flutter run`/`flutter test`/emulator runs all use debug or profile builds, which each independently carry their own dev-only `INTERNET` permission that masks this gap.
  - **Addendum (05-news-tab verifier phase, 2026-08-30):** Independently re-read all three manifest variants again this session — the gap is unchanged; `android/app/src/main/AndroidManifest.xml` still has no `INTERNET` permission. This feature (05-news-tab) is the app's **first feature making its own raw `http.Client` calls** (`lib/features/news/data/datasources/bulletins_feed_datasource.dart:24-44`, fetching `https://stlukesmarsdenpark.org.au/category/bulletins/feed/` directly via the `http` package), rather than delegating all network access to a WebView as Donate does. A release build missing this permission would therefore fail to fetch bulletins in production in exactly the same way Donate's WebView fails — the News tab's "Latest Bulletins" section would permanently show the network-failure UI state (`BulletinsMessageView`) for every production user, in addition to Donate's existing failure. This raises RISK-005's blast radius from 1 affected tab to 2, and reinforces (does not newly establish) its already-flagged higher-than-RISK-003/004 priority for Deployer.
- **Likelihood:** Certain in any release/production build, given the manifest evidence directly read this session; would not reproduce in any debug/profile-mode testing, which is why it went uncaught through Coder/Tester/Visualiser for both 03-multi-pages and 05-news-tab.
- **Mitigation:** Add `<uses-permission android:name="android.permission.INTERNET"/>` to `android/app/src/main/AndroidManifest.xml` (the manifest that actually ships in release builds), then verify with a release-mode build (`flutter build apk --release` or `flutter run --release`) that both the Donate WebView and the News tab's bulletins fetch successfully load live content. This is a manifest-only fix; no `lib/`/`test/` code changes are required. Should be treated as higher priority than RISK-003/004 for the Deployer phase, since it is a release-build correctness bug now affecting 100% of production users who open either the Donate tab or the News tab, not a subset of link taps.
- **Owner:** Deployer
- **Status:** open

- **Risk ID:** RISK-007
- **Title:** Live RSS integration tests (`bulletins_feed_live_test.dart`) are not isolated/skippable for offline or sandboxed CI runs
- **Feature:** 05-news-tab
- **Impact:** Medium. Independently confirmed this session: `test/features/news/data/datasources/bulletins_feed_live_test.dart` contains 2 ordinary `test()` blocks that make real network calls against `https://stlukesmarsdenpark.org.au/category/bulletins/feed/`, with no `@Tags`, `skip:` parameter, or runtime connectivity guard (`markTestSkipped(...)`). A project-wide search this session (`find . -iname "dart_test.yaml"`, `grep -rn "@Tags\|skip:" test/`) confirms this repo has no test-tagging convention anywhere to exclude these from a routine `flutter test` sweep. If `flutter test` is ever run in a fully offline or sandboxed CI environment, these 2 tests will report as genuine **failures** — indistinguishable in `flutter test`'s output from a real regression — rather than skips, potentially masking or being confused with an actual code defect by whoever is reading the test run. Independently re-ran the full suite and the isolated live-test file this session with network available — both pass, confirming this is currently a latent/environmental risk, not an active failure.
- **Likelihood:** Certain to manifest as a failure the first time `flutter test` runs in a network-unavailable environment (e.g. a future sandboxed CI runner); has not yet manifested since every session run so far (Coder, Tester, this Verifier phase) has had network access.
- **Mitigation:** Add a `dart_test.yaml` with a `live`/`integration` tag excluded by default (and included via an explicit `flutter test --tags live` invocation for sessions that want live-network verification), or add a runtime connectivity pre-check to `bulletins_feed_live_test.dart` that calls `markTestSkipped(...)` on failure to reach the host. This is a project-wide test-infrastructure decision (the first test-tagging convention in this repo), not a per-feature code fix, so it was intentionally not unilaterally introduced during Coder/Tester/Verifier phases for 05-news-tab. Recommended before this app's first CI pipeline is stood up, or before any future feature adds more live-network tests that would compound the same gap.
- **Owner:** Deployer (or a dedicated test-infrastructure follow-up before CI is introduced, at the user's discretion)
- **Status:** open
