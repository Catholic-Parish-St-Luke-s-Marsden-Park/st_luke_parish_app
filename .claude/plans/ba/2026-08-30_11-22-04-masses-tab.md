## Feature Summary
Replace the Masses tab's generic `PlaceholderScreen` stub with a real, static Mass-schedule screen. The screen shows a "Mass Times" hero banner (no address line) followed by exactly two sections: **"What's On"** — a single card with three ordered, labeled sub-groups (Sunday, Saturday Vigil, Weekday) listing 6 Mass rows — and **"Reconciliation & Sacraments"** — a single card listing 3 rows (Reconciliation, Baptisms & House Blessings, Sacramental Programme). All content is static, typed Dart configuration (a `MassTime`-style immutable entity, adapted from the sibling reference app's pattern but with this feature's own reduced, approved content), exposed to the UI via a Riverpod provider. No icons, no date/month display, no tappable row affordances, and no live calendar/ICS integration. This is a content-fill slice for the Masses tab only; News and all other tabs are untouched.

## In Scope
- `lib/features/masses/domain/entities/mass_time.dart` — typed, immutable `MassTime` entity with a const constructor: `time` (String, weekday-abbreviation + time only, e.g. `"Sat 5:30 PM"`), `name` (String), `note` (nullable String).
- `lib/features/masses/data/config/static_mass_schedule_config.dart` (or equivalent name under `data/config/`) — static `const List<MassTime>` definitions for each of the three "What's On" sub-groups (Sunday, Saturday Vigil, Weekday) and one for "Reconciliation & Sacraments", containing exactly the rows specified in Acceptance Criteria below. This is a static local data source, not a scraper, but lives in `data/` per CLAUDE.md's architecture guidance so it can later be swapped for a scraped/remote source without restructuring.
- `lib/features/masses/presentation/providers/` — a Riverpod provider (generated via `riverpod_generator`, consistent with the rest of the codebase) exposing the static schedule to the screen. The screen must read the schedule through this provider, not import the static config directly.
- `lib/features/masses/presentation/screens/masses_screen.dart` — replaces the `PlaceholderScreen` stub; renders the hero banner + the two sections in the order and content specified below.
- `lib/features/masses/presentation/widgets/` — small reusable widgets: a section header widget (plain text label, no icon), a card widget (rounded container grouping rows, used for both sections), and a row widget (renders `time` + `name` + optional `note`, plain text only, no icon, no tap affordance/arrow).
- Hero banner: eyebrow text "ST LUKE'S · MARSDEN PARK" + title "Mass Times", no address/subtitle line beneath it.
- Section 1 — "What's On" (single card, three labeled sub-groups in this order):
  - Sunday: `Sun 8:00 AM` / "Sunday Mass" (no note); `Sun 10:00 AM` / "Sunday Mass" (no note); `Sun 5:30 PM` / "Sunday Mass" (no note)
  - Saturday Vigil: `Sat 5:30 PM` / "Vigil Mass" / note "Reconciliation from 4:30–5:25pm"
  - Weekday: `Wed 7:30 AM` / "Weekday Mass" (no note); `Fri 6:30 PM` / "Weekday Mass" (no note); `Fri 11:00 AM` / "Marsden Park Care Community Mass" (no note)
- Section 2 — "Reconciliation & Sacraments" (single card, three rows in this order):
  - `Sat 4:30 PM` / "Reconciliation" / note "Before the Vigil Mass"
  - `By request` / "Baptisms & House Blessings" (no note)
  - `By enrolment` / "Sacramental Programme" (no note)

## Assumptions
- The exact section content, order, and copy specified in the "Approved requirements" section of the feature request (mirrored into Acceptance Criteria below) is final, sourced from the user-reviewed HTML mockup artifact; no further content changes are expected during Coder unless the user raises them.
- The `MassTime` entity's `time` field is authored as a pre-formatted display string (e.g. `"Sat 5:30 PM"`), not a structured `DateTime`/`TimeOfDay` value, since there is no sorting, filtering, or date-math requirement in this feature (consistent with the reference app's own approach). If a future feature needs structured time values (e.g. "next Mass" countdown), that would be a separate, later change.
- Because no row is tappable and no icon is required, this feature has no new external-link launches and does not touch `UrlLauncherService`, `webview_flutter`, or the RISK-003/RISK-004/RISK-005 manifest gaps carried over from earlier features.
- A single reusable card/row widget set can represent both sections despite their different sub-structure ("What's On" has three labeled sub-groups inside one card; "Reconciliation & Sacraments" has a flat row list inside one card) — Coder's call on whether the sub-group label is a variant of the same section-header widget or a distinct smaller widget, provided the three sub-group labels ("Sunday", "Saturday Vigil", "Weekday") are visually distinguishable from the two top-level section titles ("What's On", "Reconciliation & Sacraments").

## Risks
- Static content drift: since this feature does not scrape the parish website, if the parish's actual Mass schedule changes in the future, this screen will silently go stale until a developer manually updates the static config — no staleness detection exists in this feature (acceptable for Phase 1 per CLAUDE.md, but worth surfacing since a prior feature's out-of-scope note on live scraping could otherwise be read as "someday soon").
- The "By request" / "By enrolment" time-column values for the Baptisms/House Blessings and Sacramental Programme rows are non-time strings sharing the same `time` field as clock-time rows (e.g. `"Sat 5:30 PM"`). This is intentional (matches the reference app's own `"By Appt"` pattern) but Coder/Tester should confirm the row widget renders arbitrary strings in that slot correctly, not just clock-time-formatted ones, and that increased text scale doesn't cause these slightly longer strings to overflow (per CLAUDE.md accessibility rules).
- Low risk overall: no new dependencies, no new external links, no network calls — smallest-scope feature slice completed in this SDLC so far.

## Unknowns
- None blocking. All content, section order, sub-group order, icon/date exclusions, and hero copy were confirmed via the user-reviewed mockup artifact prior to this BA phase; no open clarifying questions remain.

### Architecture / data layer
- `REQ-F04-015` — The `MassTime` entity is a typed, immutable class with a const constructor (not a dynamic `Map`), defined under `lib/features/masses/domain/entities/`, with fields `time` (String), `name` (String), and `note` (nullable String).
- `REQ-F04-016` — The four row lists (Sunday, Saturday Vigil, Weekday, Reconciliation & Sacraments) are defined as static `const List<MassTime>` values under `lib/features/masses/data/config/` — not fetched over the network, not scraped, and not hardcoded inline inside a widget's `build()` method.
- `REQ-F04-017` — The screen obtains its schedule data through a Riverpod provider under `lib/features/masses/presentation/providers/` (generated via `riverpod_generator`, `.g.dart` output committed alongside its source in the same commit per CLAUDE.md's generated-code rule) — the screen/widgets do not import the static config directly.
- `REQ-F04-018` — No repository, datasource, or scraper/parser class exists under `lib/features/masses/` for reading Mass-schedule content in this feature (content is static config, not fetched) — consistent with the precedent set by 02-parish-tab's and 03-multi-pages' static-content features.
- `REQ-F04-019` — No business logic lives directly inside `MassesScreen`'s widget tree; row/card/section rendering is delegated to small, reusable widgets under `lib/features/masses/presentation/widgets/`.
