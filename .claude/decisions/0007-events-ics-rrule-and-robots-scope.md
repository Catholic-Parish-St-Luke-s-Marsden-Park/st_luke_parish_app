- **Decision ID:** ADR-0007
- **Title:** Hand-rolled, field-scoped iCalendar parsing + the `rrule`/`timezone` packages for recurrence and Sydney-local time, fetched from the AI1EC export URL despite a crawler-scoped robots.txt disallow
- **Feature:** 08-events-calendar
- **Date:** 2026-10-01
- **Status:** accepted
- **Context:** The News tab needs a live "Upcoming Events" section and a paginated "All Events" screen sourced from the parish website's AI1EC (All-in-One Event Calendar) WordPress plugin feed:
  `https://stlukesmarsdenpark.org.au/?plugin=all-in-one-event-calendar&controller=ai1ec_exporter_controller&action=export_events&no_html=true`.
  Three questions needed resolving: (1) how to parse the RFC 5545 iCalendar feed, materially more complex than News' RSS+regex approach (recurrence rules, timezone-qualified date-times, line folding); (2) how to handle recurring events (Masses, regular groups), which the feed represents as `RRULE`-bearing `VEVENT` templates, not pre-expanded instances; (3) whether fetching the export URL is acceptable given `robots.txt` disallows `/*controller=ai1ec_exporter_controller*` (grouped with other crawler/SEO-indexing directives and a full block on `MJ12bot`).
  This same parish already runs another app, `stlukes-marsden-park-app` (a Netlify-deployed PWA, found on the user's own machine during this feature's BA phase) — its `netlify/functions/events.mjs` is a live, production implementation fetching this exact URL, confirming it works, that recurring events are `RRULE` templates, and the `DTSTART;TZID=Australia/Sydney` floating-local-time format. It only computes each template's *next* occurrence, which is not sufficient for this feature's own paginated "View all upcoming events" screen.
- **Decision:**
  1. **Parsing:** a hand-rolled parser (`lib/features/events/data/parsers/ics_event_parser.dart`) scoped to exactly the fields needed (`SUMMARY`, `DESCRIPTION`, `LOCATION`, `DTSTART`, `DTEND`, `UID`, `URL`, `RRULE`), including RFC 5545 line unfolding — following this project's established preference (News' RSS+regex) for lean, purpose-built parsing over a general-purpose library for the *field-extraction* step.
  2. **Recurrence expansion:** the `rrule` package (`^0.2.18`) is used for `RRULE` parsing/expansion (`RecurrenceRule.fromString(...).getInstances(start:, after:, before:)`), rather than hand-rolling `FREQ=WEEKLY`/`DAILY`/`UNTIL`/`COUNT` logic — a mature, purpose-built package exists for exactly this well-specified sub-problem, unlike feed-shape extraction, which is specific to this one site. Expansion is bounded to a 180-day lookahead (`eventsLookaheadDays`), computed once per fetch; the inline 7-day section and the paginated All Events screen both slice this same already-expanded in-memory list rather than re-fetching or re-expanding per page.
  3. **Timezone handling:** a hybrid of two techniques. (a) The reference PWA's "fake UTC" trick — treating a `TZID=Australia/Sydney` (or Z-suffixed) date-time's digits as literal `DateTime.utc(...)` fields — is used throughout for `DTSTART`/`DTEND` parsing and `RRULE` stepping, so weekly/daily recurrence arithmetic reproduces the same wall-clock time every occurrence with no DST-shift distortion. (b) Unlike the reference PWA (which computes "now" via JS's `Intl.DateTimeFormat`), this feature uses the `timezone` package (`^0.11.1`, already a transitive dependency via `flutter_local_notifications`, now declared directly) to compute the current `Australia/Sydney` wall-clock time correctly across the AEST/AEDT transition, then converts that into the same fake-UTC representation (`sydneyNowAsFakeUtc()`) so it composes directly with the rest of the parsing/filtering/sorting logic. A fixed UTC+10/+11 offset was rejected as silently wrong for roughly half the year.
  4. **robots.txt:** proceeding on the reading that the disallow rule is crawler/SEO-indexing-scoped (it disallows every date-permutation export URL from being indexed, alongside a full block on `MJ12bot`), not a prohibition on a single legitimate client fetch — reinforced by direct evidence that the parish's own other app already fetches this exact URL from a live server in production, and that the site's own in-page "Add to Calendar" buttons link to this same URL for this same purpose. Confirmed explicitly with the user during the BA phase before this Coder phase began.
- **Alternatives Considered:**
  - A pub.dev ICS-parsing package (e.g. `icalendar_parser`) for the whole feed-shape extraction, not just recurrence — rejected for this feature: the BA plan's own live-feed inspection was blocked by this session's web-fetch tooling, but the reference PWA's working code gave enough confidence in the feed's actual shape that the leaner, News-precedent-matching hand-rolled approach was preferred; a general ICS package remains a reasonable fallback if Coder's own live-feed fetch during implementation finds structure the hand-rolled parser can't safely cover.
  - Hand-rolling `RRULE` expansion instead of using the `rrule` package — rejected: unlike feed-shape extraction, `RRULE` expansion is a well-specified, site-independent RFC 5545 sub-problem a mature package already solves correctly, and hand-rolling it would be pure risk with no site-specific benefit.
  - A fixed UTC+10/UTC+11 offset instead of the `timezone` package for computing "Sydney now" — rejected: silently wrong for roughly half the year across the AEST/AEDT transition, and the `timezone` package was already a transitive dependency, so declaring it directly cost nothing new.
  - Not fetching the feed at all / asking the parish webmaster for an alternative URL first — considered and explicitly raised with the user during the BA phase; the user chose to proceed on the robots.txt reasoning above rather than delay on this.
- **Consequences:** No CSS-selector-based scraping is added for events, so `.claude/context/selector-registry.md` does not gain an events entry (same precedent as ADR-0004). This feature adds three new direct dependencies (`rrule`, `timezone`, `add_2_calendar`) — `timezone`'s transitive-to-direct promotion has no version-resolution risk since the locked version is unchanged. If the live feed's actual `VEVENT` shape differs from what the reference PWA's code assumes (not independently re-verified against raw feed bytes during this BA/Coder phase — see the BA plan's Unknowns), individual malformed blocks are skipped rather than failing the whole fetch (REQ-F08-004), so a partial shape mismatch degrades gracefully rather than breaking the section entirely; Tester should still perform a live fetch early, per `CLAUDE.md`'s scraping-verification rule, to confirm nothing was missed.
