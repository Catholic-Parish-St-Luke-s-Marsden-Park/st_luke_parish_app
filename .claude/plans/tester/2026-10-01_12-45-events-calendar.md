## Independent Re-Verification (before trusting or extending any test)
Read every implementation file directly and cross-checked against each REQ-F08-* acceptance criterion:

- `parish_events_feed_datasource.dart` — fetches `ExternalLinks.eventsFeed` via an injected `http.Client`, 10s timeout, the same `User-Agent` convention as Bulletins, converts every thrown exception and every non-200 status into `EventsNetworkFailure` (REQ-F08-001 ✅).
- `ics_event_parser.dart` — field-scoped regex extraction of `SUMMARY`/`DESCRIPTION`/`LOCATION`/`DTSTART`/`DTEND`/`UID`/`URL`/`RRULE`, RFC 5545 line-unfolding (`\r\n `/`\n ` continuation removal, REQ-F08-002 ✅); `DTSTART`/`DTEND` parsed via the "fake UTC" technique for both `TZID=`-qualified and `Z`-suffixed full date-times, plus a separate date-only (all-day) branch (REQ-F08-003 ✅, independently confirmed against the real live feed — see below); a block missing `SUMMARY`/`DTSTART`, or any other unexpected per-block exception, is skipped via `onSkippedBlock` and `continue`, never thrown to the caller (REQ-F08-004 ✅); `RRULE` expansion via `RecurrenceRule.fromString('RRULE:${rruleField.value}')` + `getInstances(start:, after:, before:)`, bounded to a 180-day lookahead, with a graceful single-occurrence fallback on an unparseable `RRULE` (REQ-F08-006 ✅).
- `feed_events_repository.dart` — sole `EventsRepository` implementation; orchestrates fetch → parse → an explicit ascending sort by `start` (independent of block/expansion order, REQ-F08-005's sort clause ✅) → maps to the typed `ParishEvent` entity, validating the optional per-event `URL` (scheme+host check) before exposing it as `detailUrl` (REQ-F08-023 ✅); converts every failure to `EventsFailure` subtypes, with an empty-response-body special case treated as `EventsParsingFailure` rather than a false empty result (REQ-F08-009, REQ-F08-010, REQ-F08-011 ✅).
- **Found: REQ-F08-005's past-event filter is narrower than specified.** REQ-F08-005 says to exclude events whose *end* (falling back to *start* only when no end is known) is in the past. All three of `parseIcsEvents`'s filtering branches (plain single-occurrence, the `rrule` package's own `after: now` parameter, and the unparseable-RRULE fallback) instead compare `start` alone against `now`, even when a `DTEND` (and therefore a known duration) is available. A currently-in-progress event (e.g. a Mass checked 10 minutes after it started, 20 minutes before it ends) is incorrectly excluded for its own duration. Logged as **RISK-014** (`.claude/risks/active-risks.md`) rather than fixed blind this phase — the correct fix touches recurrence-expansion timing logic, including widening the `rrule` package's own `after:` bound, which this session cannot verify by actually executing `flutter test` against a real clock-dependent scenario. Recommended as a small, deliberate Coder follow-up (see the risk entry for the exact approach).
- `events_provider.dart` — `@riverpod eventsRepositoryProvider` wires `FeedEventsRepository`; `@riverpod upcomingEventsProvider` exposes `Future<List<ParishEvent>>` (`AutoDispose` by generator default — REQ-F08-012 ✅). `events_section.dart`/`all_events_screen.dart` are the only widgets reading events, both via `ref.watch(upcomingEventsProvider)` — confirmed via `grep -rn "eventsRepositoryProvider\|FeedEventsRepository\|ParishEventsFeedDatasource\|parseIcsEvents" lib/features/events/presentation/` finding no hits outside `events_provider.dart` itself (REQ-F08-013 ✅).
- `events_section.dart` — `.when(loading, error, data)`: loading renders `EventsLoadingView` (REQ-F08-014 ✅); success slices the already-sorted full list to `start.isBefore(now + 7 days)` for the inline list (REQ-F08-015 ✅); a fully-empty list (0 events anywhere) renders `EventsMessageView` with the website fallback link and no "View all" link (REQ-F08-016, REQ-F08-021 ✅); a non-empty full list with 0 events in the next 7 days renders a distinct message *and* the "View all upcoming events" link, not the website fallback (`showWebsiteLink: false`) — confirmed this is genuinely conditional on which case, not just always-both (REQ-F08-017 ✅); `error` branch distinguishes `EventsNetworkFailure` vs. other with different copy (REQ-F08-018, REQ-F08-019 ✅), both via the shared `EventsMessageView`'s fallback link wired through the real `UrlLauncherService` abstraction (REQ-F08-020 ✅).
- `event_row.dart` — date/time pill + bold title + italic location (only when non-null) + a `Wrap` of two independent 48x48-minimum `InkWell` tap targets, "Details" and "Add to my calendar" (REQ-F08-022 ✅); the `Wrap` (not a fixed-width `Row`) is the same text-scale-overflow precedent as `BulletinListTile`/`MassRow`.
- `event_details_sheet.dart` — `showModalBottomSheet` rendering title/displayTime/location/description entirely from already-parsed `ParishEvent` fields, no network call; an optional secondary "View on parish website ↗" link only when `detailUrl != null`, launched via `UrlLauncherService`; an explicit "Close" tap target plus the platform-standard swipe-down/back dismissal (REQ-F08-023 ✅).
- **Found and fixed: `add_to_device_calendar.dart` called `Add2Calendar.addEvent2Cal` directly (a static plugin call), with no injectable seam** — unlike every other external-effect call site in this app (`UrlLauncherService`), this meant REQ-F08-039(d)'s "unit/widget tests confirming 'Add to my calendar' triggers export with correct event data" could not be satisfied without touching real platform channels in a widget test (the same class of problem noted for `webview_flutter` during 03-multi-pages). - `all_events_screen.dart` — pushed via `Navigator.push`/`MaterialPageRoute` from `EventsSection`'s "View all" link only, not a new tab/drawer entry or a registered `go_router` route (REQ-F08-027 ✅ — this corrects what the BA plan's own REQ-F08-027 text said, "registered via go_router"; the coder plan already flagged this correction, independently confirmed correct against this app's actual navigation conventions, where every other pushed sub-screen — Resources, Prayer Request — uses plain `Navigator.push` too); lists the full list with no 7-day limit, same `EventRow` (REQ-F08-028 ✅); paginates via a `ListView.builder` + "Load more" button over the already-expanded in-memory list rather than rendering/building every remaining row at once (REQ-F08-029 ✅); reuses `EventsLoadingView`/`EventsMessageView`/`EventRow`, no duplicated UI logic (REQ-F08-030 ✅).
