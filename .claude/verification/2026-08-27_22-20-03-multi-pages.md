## Platform Manifest / Risk Re-Verification (direct file reads this session)

### RISK-003 (Android `<queries>` gap) — re-confirmed still open, unchanged
Read `android/app/src/main/AndroidManifest.xml` directly this session. It still contains only a `PROCESS_TEXT` `<queries>` entry — **no** browsable `http`/`https` `VIEW`-intent `<queries>` block exists. This means `url_launcher`'s `canLaunchUrl` will continue to silently fail on Android 11+ for every `https:` launch this feature adds (Ministries "Join Us" CTA is `mailto:`, not affected the same way, but Contact's Facebook/Website/Google-Maps `https:` launches are directly affected the same way REQ-F02-005/006/007 were). RISK-003 in `active-risks.md` is accurate and applies unchanged to this feature's new launch points — no manifest change has been made since 02-parish-tab's verifier phase flagged it.

### RISK-004 (iOS `LSApplicationQueriesSchemes`) — re-confirmed still open, unchanged
Read `ios/Runner/Info.plist` directly this session. No `LSApplicationQueriesSchemes` key exists, unchanged since 02-parish-tab's verifier phase. Still unconfirmed either way for this feature's new launch points.

### `tel:`/`mailto:` schemes specifically — not directly covered by RISK-003/004's wording
RISK-003's wording (carried over from 02-parish-tab) was written specifically about `https:` leadership links. This feature adds the *first* `tel:`/`mailto:` launches in the app (Ministries CTA is `mailto:`; Contact Phone/Mobile are `tel:`, Email is `mailto:`). Android's package-visibility `<queries>` requirement (API 30+) applies per-intent-scheme, not just to `https`: a `<queries>` block scoped only to `action=VIEW, category=BROWSABLE, data scheme="https"` (the standard fix suggested for RISK-003) would **not** cover `tel:`/`mailto:` intent resolution — those need their own `<data android:scheme="tel"/>` / `<data android:scheme="mailto"/>` (or an `ACTION_DIAL`/`ACTION_SENDTO` `<queries>` entry) to be reliably resolvable by `canLaunchUrl` on Android 11+, depending on whether the device has a matching dialer/mail app that participates in package visibility. This is a refinement of RISK-003's scope, not a new risk — logged as an addendum to RISK-003 in `active-risks.md` so the eventual manifest fix (owned by Deployer) covers `tel:`/`mailto:` schemes too, not just `https:`.

### `webview_flutter`'s own manifest/entitlement requirements — new finding, distinct from RISK-003/004
Checked whether `webview_flutter` introduces its own Android manifest or iOS entitlement requirement, separate from the `url_launcher` risk:
- **Android:** `webview_flutter_android`'s underlying `android.webkit.WebView` requires the app to hold `android.permission.INTERNET` to make any network request. Read all three Android manifest variants directly this session:
  - `android/app/src/debug/AndroidManifest.xml:6` — has `<uses-permission android:name="android.permission.INTERNET"/>` (with a comment stating it's "required for development" — hot reload/DevTools, a debug-only concern)
  - `android/app/src/profile/AndroidManifest.xml:6` — same, also debug/profile-only
  - `android/app/src/main/AndroidManifest.xml` (the manifest merged into **release** builds) — **has no `INTERNET` permission at all**, and `android/app/build.gradle.kts` has no manifest-merger override that would add one
  - This means a **release** Android build of this app has no `INTERNET` permission. The `WebView` in `SimpleWebViewScreen` would be unable to make any network request in a release APK/AAB — `loadRequest` would fail immediately, and the app would show the "Unable to load this page" error state to every user, permanently, in production. This is a genuinely new, previously-uncaught gap: no prior phase (BA, Coder, Tester) checked this, and Visualiser's live run used `flutter run -d emulator-5554` (a **debug** build, which inherits the debug manifest's `INTERNET` permission), so this gap would not have reproduced during that session and was not caught. This is analogous in kind to 02-parish-tab's verifier phase catching the AndroidManifest `<queries>` gap that no prior phase had checked — logged as **RISK-005** below.
  - **Android:** `INTERNET` is a normal (not dangerous) permission with no user-facing runtime prompt, so once added, no additional runtime-permission handling is needed.
- **iOS:** `WKWebView` (via `webview_flutter_wkwebview`) does not require any special entitlement or `Info.plist` key for loading standard `https:` content — no App Transport Security exception is needed since the donate URL is `https:` on a standard port. Confirmed no ATS-related `Info.plist` keys exist or are needed. No iOS-specific gap found for `webview_flutter` itself, distinct from RISK-004 (which is about `url_launcher`, not `webview_flutter`).

## New Risk Logged

**RISK-005** — logged in `.claude/risks/active-risks.md` (Open Risks): the release/`main` AndroidManifest is missing `android.permission.INTERNET`, which is required for `webview_flutter`'s `WebView` (Donate tab) to make any network request in a release build. Currently masked in all local/CI testing because `flutter run`/`flutter test` and the Visualiser's live emulator run all use debug or profile builds, which each carry their own dev-only `INTERNET` permission. This is a release-build-only failure mode that would not reproduce in any of this feature's current test/visualiser evidence.

## Verdict

**Conditional pass.**

All 29 requirements (REQ-F03-001..029) are fully implemented with complete, independently-verified code and test traceability — no gaps, no mismatches between self-reported and actual implementation. Both documented ADR deviations (0002, 0003) are correct, intentional, and consistent with the BA plan's actual intent, not unauthorized drift.
